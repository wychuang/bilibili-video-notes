Agent 真正在做什么：沿执行轨迹看运行框架

来源：B 站原讲解 · Claude Code 与 Harness · 49 分钟 · 标准学习稿。视频包括运行轨迹演示与作者对旧版代码的分析；后者提及非正式披露版本，不能视为当前官方实现证明。本篇只提炼通用结构，不转载相关源码。

一句话抓住核心

模型提出下一步，运行框架决定它能否执行、怎样执行、如何把结果交回模型，以及什么时候结束。

“帮我读 README”后面发生了什么

用户只输入一句话。系统先把任务、规则、可用工具和会话状态组织成请求；模型返回读取文件的工具调用；程序检查参数与权限，再执行读取；文件内容作为工具结果进入下一轮。[00:02:45]

如果模型已经能回答，就结束这一轮任务；如果还要查别的文件，则继续。这条循环是理解 Agent 的主干：

准备上下文 → 请求模型 → 检查行动 → 执行工具 → 回传结果 → 再次判断。

注意两个区别：输出一个工具调用只表示意图；工具成功返回，也不代表用户的整个目标已经完成。

一条用户消息，可能触发多种请求

演示中，系统先生成会话标题，再进入主要任务循环。标题请求和实际做事的请求目的不同。分析调用次数与成本时，应把辅助请求单独辨认出来。[00:06:50]

后续请求会带入历史消息和工具结果。项目规则、时间、工作目录等上下文，也可能由运行框架自动加入。用户看到的聊天记录通常只展示了其中一部分。[00:08:00]

这提示了一种排查方法：发现回答异常时，查看实际送入模型的请求结构，确认规则与资料是否被加载。日志包含敏感数据时，应先脱敏，再分享最小必要片段。

五块职责，比记源码函数名更有用

部分 负责什么 对应的体验问题
入口与界面 接收输入、显示过程、响应取消 用户是否知道任务还在运行？
应用编排 配置、命令、扩展、任务安排 当前启用了哪些能力？
核心运行循环 模型请求、工具执行、上下文管理 下一步怎样决定，循环怎样结束？
状态与观测 会话恢复、执行记录、成本与延迟 出错后能否定位、恢复？
外部环境 模型服务、文件、网络、远程工具 依赖失败或权限变化时怎么办？

这张表是对视频结构的归纳，便于跨产品比较。具体函数名和内部边界随版本变化。[00:11:20]

为什么长任务需要事件流

任务可能运行几分钟。如果程序只在最后返回一个结果，界面中间就像卡住了。视频用异步事件解释：新文本、工具开始、工具结束、错误等，都可以逐步交给界面显示。[00:20:12]

事件流既改善等待体验，也让不同入口复用同一套执行逻辑。终端、网页或 SDK 可以消费相同类型的事件，分别呈现给用户。

好的进度提示应说明正在处理什么、已经得到什么、是否需要用户决定。不断转圈或反复说“处理中”，信息价值很低。

工具需要两份说明

对模型，要说明工具名、用途和参数结构。对执行器，还要说明是否可用、怎样检查权限、怎样执行、是否允许并发、怎样处理异常。[00:27:40]

例如读取两个独立文件可以并行；同时改同一个文件就可能互相覆盖。一个命令被模型描述为“只读”，仍应由程序检查。无法可靠判断的复合操作，需要更保守的处理。

MCP 工具接入后也应遵守同样的执行边界。协议连接让调用形式更统一，不会自动消除远程服务的错误、敏感信息风险或授权要求。[00:32:10]

上下文压缩：续上任务，也可能丢掉关键约束

演示中，手动压缩把较长历史整理成摘要，下一轮使用摘要继续。原始细节可能保存在另一个记录中，需要时再查。[00:44:20]

评测压缩质量，不能只看摘要短了多少。还要检查用户最新要求、已完成事项、未解决错误、关键证据位置以及禁止事项是否保留。少掉一句“不要覆盖原文件”，可能比少掉整段闲聊严重得多。

视频也展示了子任务委派：主任务派出独立工作，等待结果再整合。并发应有清晰边界，避免重复搜索、冲突写入与把一个子任务的失败藏在总结果里。[00:41:35]

迁移练习：做一张最小执行轨迹表

找一次可安全重现的 Agent 失败，记录五列：步骤、预期行动、实际工具与参数、返回结果、下一步决策。只保留必要信息，删除令牌、私人文件内容和真实账号。

然后判断问题发生在哪里：模型选择错了、参数不合法、工具没执行成功、结果没被理解，还是任务早早宣告完成？每个标签都要指向一条可观察记录。

补充边界：本课讲解中的 API 格式、工具列表和压缩细节都是录制时的例子。实际接入前应核对目标服务当前文档，不能仅通过更换模型名推定接口兼容。
