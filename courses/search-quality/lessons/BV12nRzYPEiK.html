统计学生人数，为什么该把查询交给数据库？

来源：code秘密花园｜MCP + 数据库，一种提高结构化数据检索精度的新方式 · 25 分 17 秒 · 深度阅读

“有多少身高大于 180、姓李的男同学？”这句话看起来很容易理解，真正回答时却有一个严格要求：所有满足条件的人都要算进去，任何不满足条件的人都不能算进去。假如系统只找回几段与“身高”“李同学”相似的文字，语言模型即使把眼前的人数数对，也可能漏掉没有被检索回来的其他同学。

这个例子让我们看见两种不同工作。找到几段相关资料，可以帮助解释一个概念；对完整记录进行条件筛选和计数，则需要确认范围没有漏掉。数据库本来就擅长后一项工作。我们要做的是让模型把自然语言问题转换成合适的查询，由数据库执行，再把查询结果解释给用户。MCP 在这里帮助连接模型应用与数据库工具，使这条过程更容易搭起来。

先弄清普通知识库在什么地方容易漏掉信息

常见的向量检索式 RAG，会先把文档切成较小片段，再把片段转换成向量。用户提问时，系统比较问题与片段的相似程度，取回其中一些内容，交给语言模型回答。这个办法适合从大量文字中缩小阅读范围，但返回的片段通常只占全部资料的一部分。我们不能因为这些片段很相关，就自动认为它们已经包含全部符合条件的记录。

“列举所有……”和“总结整个……”一类问题，尤其容易遇到这个困难。检索到一段说明，可能足够回答局部细节；想把一个集合列全，就需要知道还有哪些内容没被看到。固定取回若干片段的简单流程，通常无法仅凭片段本身判断数量是否已经足够。把统计问题交给这种流程时，漏找一步就可能影响最后的数字。

文档之间还可能有需要保留的关系。例如，新说明可能修改了旧说明，某个条件可能在另一份文件里。若返回片段没有带上这些关系，模型就难以知道哪份适用。更复杂的检索系统可以增加版本信息、多轮查询和其他处理；这里讨论的局限，主要针对那种切片、检索一次、直接回答的简化流程，不能据此认定所有 RAG 都只能这样工作。

学生信息恰好提供了另一种选择。姓名、性别、身高、成绩等内容本来就有明确字段，我们可以保留字段结构，直接查询这些条件。这样，系统不用先猜哪几段文字最像“高个子的李同学”，数据库可以在约定的数据范围内逐条判断记录是否满足要求。

模型能说出一个查询，与程序真的执行查询，还隔着一步

工具调用，通常也叫 function calling，提供了模型与外部程序配合的一种方式。我们先向模型说明有哪些工具、每个工具负责什么、需要哪些输入。模型遇到相关任务后，可以提出一个带参数的调用请求。运行模型的应用接住请求，调用实际工具，把结果送回模型。最后，模型根据工具返回的内容回答用户。

查询天气是一个容易理解的例子。模型仅凭训练时的文字，无法知道此刻某地的天气；它可以提出“查询这个城市天气”的请求，由真正连接天气服务的程序取得结果。数据库查询也一样。模型负责理解需求和形成调用，数据库工具负责把请求执行出来。模型写出“查询成功”几个字，与工具确实返回成功结果，需要分别看待。

如果每个应用对工具的描述方式、调用格式和返回格式都不同，开发者接入同一种能力时就可能重复做适配。一个文件工具在某个聊天应用里可以使用，换个应用又需要重新连接。这种重复工作，正是统一协议希望减少的部分。

MCP 把连接方式统一起来，各部分仍然有自己的职责

MCP 的全称是 Model Context Protocol，模型上下文协议。它约定模型应用怎样与提供工具或数据的服务通信。可以把它想成统一接口：数据库工具按这个协议提供能力，支持协议的应用就有机会复用它。统一接口不会替数据库计算结果，也不会替模型理解用户的问题；它让两边交换能力说明、请求和结果有共同格式。

图里有三个需要认识的名称。Host 是用户实际操作的应用，例如聊天客户端或编程助手。Client 在应用内部负责与某个服务建立连接。Server 是提供具体能力的程序，可能连接数据库，也可能读取文件或控制浏览器。用户先在 Host 中提出问题，应用再借助 Client 与 Server 通信，Server 最后访问真正的数据源。

有了这个分工，就容易理解为什么协议兼容与模型能力需要分别确认。客户端能够连接某个 MCP Server，只说明它们可以按共同规则通信；模型能否选对工具、填写正确参数，还与模型和应用的实现有关。不同客户端也可能采用不同方式把工具介绍给模型，所以某个客户端可以使用的模型，不一定在另一个客户端里有完全相同的表现。

除了可执行的工具，MCP 还涉及其他类型的内容。这里介绍的几种能力可以放在一起看，不用一次记住所有接口细节。我们当前的数据库案例主要使用 Tools，因为它需要执行查询并取回结果。

名称 可以怎样理解
Tools 可调用的操作，例如查询数据库或读取文件
Resources 服务提供、可作为上下文读取的数据或内容
Prompts 服务提供的可复用提示词模板
Sampling 服务通过客户端请求模型帮助完成某项生成工作
Roots 客户端告知服务需要关注的资源位置

从列出文件开始，先确认一条工具调用真的走通了

最小的体验案例使用文件系统工具。给客户端配置这个服务时，需要指定允许访问的目录。这样，服务才知道这次开放的文件范围在哪里。随后在聊天中询问目录里有哪些文件，模型提出读取请求，工具返回列表，模型再把列表整理成回答。继续要求在这个目录写入一个文件，就能看到写入操作与最终文件之间的对应关系。

这个例子的价值在于把抽象的协议变成可观察的动作。我们在聊天窗口提出要求，外部程序实际读取或写入，结果回到聊天窗口。它也让权限问题变得具体：列目录和创建文件是两种操作，只读任务不需要自动获得全部写入权限。接到真实资料时，应按任务限制范围，不能因为工具能访问文件，就把所有目录都交给它。

录制时的体验从 Cherry Studio 开始，随后转到 VS Code 中的 Cline 插件。两种客户端的界面和工具调用实现有所不同，示例中也遇到了模型支持范围与稳定性的差异。理解这部分时，可以抓住共同步骤：选择应用、连接需要的服务、确认模型能使用工具、检查实际返回。按钮位置和兼容列表会随版本变化，不必把当时的界面当作固定规范。

学生、教师和成绩，先保存在数据库里

接下来的数据库使用 MongoDB。它是一种文档型数据库，数据以类似 JSON 的文档形式组织。一个集合中的文档可以比较灵活地增加字段，对持续补充的结构化资料较方便。这个选择展示了一种实现路径，关系型数据库同样可以处理许多条件筛选与关联任务；是否需要 MongoDB，要看原有数据和实际需求。

示例把学生、教师、成绩和班级信息导入数据库，再通过 MongoDB Compass 这样的图形客户端查看数据。Compass 是查看和管理数据的界面，真正保存并执行查询的是数据库服务。把这两个角色分开，就能理解后面的模型为什么不需要模拟人去点击每一行记录：它通过工具连接数据库服务，直接提交查询。

原始资料如果是一张表，也可以先转换为适合导入的记录。导入之后，我们需要知道各集合里放了什么，字段分别表达什么，以及记录之间怎样对应。学生信息里有姓名，不代表成绩也一定放在同一处。后面的一次失败，正是从这个差别开始的。

数据内容 在问答中解决什么问题
学生信息 找到符合姓名、性别、身高等条件的学生
教师信息 查到与某位教师有关的获准公开信息
成绩信息 比较同一个学生不同考试的成绩
班级及关联信息 把学生、课程或教师关系联系起来

连接数据库的 MCP Server 相当于把数据库操作包装成可调用工具。配置中常见的 command 表示如何启动服务，args 表示传给启动命令的参数。示例使用依赖 Node.js 的启动方式，并传入数据库连接信息。配置里还提供只读模式，用来限制服务可以执行的操作。我们可以理解这些参数分别负责什么，不需要把示例里的所有权限原样带到自己的数据上。

条件计数很顺利，成绩比较却先查错了地方

先试“有多少身高大于 180、姓李的男同学”。这句话需要同时保留三个条件，再统计满足条件的记录数。只找到几个身高较高的学生不够，只找到姓李的人也不够。数据库查询把条件组合起来，让它们共同决定哪些记录可以被计入。示例中的这项查询得到了符合预期的结果。

再试“哪些同学期末考试成绩比平时考试成绩好”。我们听到这句话，可以立刻想到比较两种分数；模型却还不知道数据库里哪两个字段代表它们，也不知道成绩存在哪个集合。第一次提出的条件因此不正确。工具虽然已经连上数据库，模型对数据组织方式的了解仍然不足。

随后，模型开始查看正在访问的集合有哪些字段。发现其中没有所需的成绩信息，就继续列出其他集合，找到分数相关的集合，再查看里面的字段。等两种成绩对应的位置清楚以后，它才构造出较合适的查询。整个过程很像我们第一次接手一份陌生数据库：先找资料存放的位置，再确认字段含义，最后才能比较数值。

这条失败很值得停下来想清楚。MCP Server 已经完成了提供数据库访问能力的工作；出现问题的地方，是模型还缺少正确写查询所需的结构信息。重新配置连接并不能补上这项知识，继续扩大权限也没有帮助。我们需要让模型知道数据在哪里，以及各字段究竟是什么意思。

把数据结构说清楚，减少猜测与来回探查

改进办法是在上下文中预先写出数据结构及使用要求。Schema 可以理解为数据库的结构说明，包括有哪些集合或表、包含什么字段，以及它们怎样关联。示例还明确要求：涉及学生、教师或成绩的问题，应通过 MongoDB 工具查询。这样，模型在形成第一条查询之前，就有机会读到所需的背景。

再次问成绩比较问题时，模型更直接地提出了查询思路，返回了比较结果，还按进步分数进行了排序。这次变化的原因很容易追踪：模型一开始就知道相关数据的位置与含义，少走了先猜字段、查错集合、再四处寻找的几步。查询工具没有因此获得新的魔法能力，输入给模型的说明变得更充分了。

结构说明本身也需要与数据库保持一致。假如字段已经改名，说明仍然使用旧名字，模型就可能重新走错。给模型更多上下文的目的，是提供准确且与当前任务有关的信息；一份陈旧或含糊的字段介绍，会把错误从“猜测”变成“按错误说明执行”。因此，schema 说明与实际记录需要一起理解。

形成查询前模型知道什么 容易发生的情况 需要补上的信息
只知道数据库可以访问 猜集合或猜字段，先查错位置 数据存放位置和字段含义
看过集合列表，还没看过字段 找到成绩集合，但仍可能比较错字段 两种考试成绩各对应哪个字段
获得准确结构说明与查询要求 更直接地组织筛选、比较和排序 继续检查实际查询是否保留用户条件

从一个学生找到他的老师，需要把关系接起来

更复杂的例子是：“有个学计算机的周同学，给我他的老师的联系方式。”这句话包含不完整的姓名，还有一层人物关系。系统要先在计算机专业的学生里找到符合称呼的人，再通过已有关系找到对应教师，最后读取相关字段。仅仅找到一段同时出现“计算机”和“周”的文字，并不保证这些关系已经接对。

示例中，模型通过组合查询找到了对应学生和教师。这个过程说明，结构化数据的价值还包括记录之间的关系。问题从学生出发，答案却在教师信息中，需要数据库里的关联帮助连接。真实使用时，如果符合条件的学生有多位，就需要进一步确认，不能任意选择一人；联系方式也只能在有访问权限与适当用途的范围内查询和使用。

把条件与关系表达清楚，是这个案例比单纯语义匹配更有优势的地方。模型仍然负责理解“学计算机的周同学”是什么意思，但确定条件之后，数据库可以按照数据中已有的关系执行查找。每个环节都有可以检查的对象：学生是否选对，教师关系是否对应，最后读取的字段是否属于那位教师。

同样的数据放入普通知识库，差别在哪里

比较环节把同一份学生数据导入普通知识库，再询问学生总数、条件筛选和成绩比较等问题。较简单的问题可以得到可用结果，更复杂的比较没有顺利完成。对这组结构化任务，数据库路线表现出了优势，因为它能够直接执行筛选、计数和记录关系查询。

这个结果与任务特点是对应的。计算人数要求完整范围，比较成绩要求同一学生的字段对应，查教师要求关系正确。数据库对这些操作有明确表达方式。普通切片检索如果只是返回一部分相关材料，语言模型就可能缺少完成这些操作所需的全部记录。

这组对比也有边界。它比较的是示例所使用的知识库配置与数据库工具流程，无法由此断定所有 RAG 系统在所有任务上都更差。检索文字资料和查询数据库可以在同一应用里共同工作。理解眼前数据适合怎样查，已经足以解释这个案例的主要价值，无需再把技术名称分成绝对赢家和输家。

查询能力更直接，也需要限制返回范围

数据库可以按条件查询很多记录。如果一次把大量记录原样交回模型，上下文会快速增长，费用和等待时间也可能增加，客户端甚至可能难以处理。用户只问人数时，返回全部学生的每个字段通常没有必要；应让查询完成与问题对应的计算，并控制返回内容的范围。这个区别让“能查询”进一步变成“查询得合适”。

工具描述、数据结构说明和多轮调用记录，同样会占用上下文。示例中观察到的额外消耗，与所用客户端怎样向模型提供工具信息有关，不能直接理解为协议在任何实现下都会固定增加同样多的费用。对当前应用，值得观察的是一次任务实际调用了多少次、每次返回多少内容，以及哪些探查可以通过准确说明减少。

回到开头的学生计数题，我们现在可以完整走一遍：模型理解三个条件，应用调用获准使用的数据库工具，数据库在限定范围内筛选并计数，模型再解释返回结果。MCP 帮助连接这几部分，结构化记录帮助保留条件，而准确的数据说明帮助模型提出合适查询。几个角色配合起来，才形成了这次可用的回答。

总结提炼

一句话抓住核心

需要精确计数、字段比较和关系查询时，可以让模型提出查询、数据库执行计算；MCP 负责连接工具，schema 说明帮助模型把条件写对。

推理主干

只找回相似片段可能漏掉符合条件的记录。数据库能够直接筛选与计算，但模型仍要知道集合、字段和关系。成绩比较的失败说明连接成功还不够，补充准确结构说明后，模型才更容易提出合适查询。最后还需要限制权限与返回量。

复习与行动清单

补充练习：准备一份完全虚构的十行书单，包含书名、作者、年份和页数。先手工回答一个计数问题、一个多条件筛选问题和一个字段比较问题，再检查模型提出的查询。把“条件理解正确”“查询表达正确”“结果解释正确”分别看一遍，就能分清一次失败究竟发生在哪里。
