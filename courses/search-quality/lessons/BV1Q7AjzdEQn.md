# 第一版能运行，第二天还能交付吗：两个 AI 内容站的产品复盘

> 来源：Vibe Coding 实战复盘：做玩具容易，做产品难  
> UP 主：李自然说 · 27 分 2 秒 · 深度阅读  
> 链接：https://www.bilibili.com/video/BV1Q7AjzdEQn/

让 AI 做一个抓取新闻的小网站，第一天可能很顺利：页面生成了，新闻也有了，排版看起来不错。第二天继续运行，却发现头条还是昨天那件事，只是换了一家媒体报道。把相似内容全部删掉以后，又发现某个事件明明有重要进展，也一起被过滤了。程序每天都在运行，读者得到的内容却未必每天都有新价值。

李自然做的 AI 资讯速览与 AI 论文简报，就需要处理这类问题。前一个站从多个英文信息源整理资讯，后一个站从大量论文中挑选少数内容，用容易理解的方式讲给读者。这两个个人项目让他体会到，生成一版看起来完整的页面，与让产品持续交付有用内容之间，还有很多具体工作。[00:00:00] [00:13:27]

他用很悬殊的难度比喻区分炫目的展示、自用工具和长期公开产品。数字表达的是个人感受，并非统一测量。真正值得顺着理解的，是难度增加在哪里：维护方式、内容判断、写作质量，以及事情出错以后怎样继续。

## 技术选择先回答：这个站准备怎样长期活着

两个站都是个人信息项目，李自然不准备每天投入大量精力维护，也没有复杂交易、动态广告或个性化推荐的要求。最重要的条件因此很明确：内容可以定期更新，读者能够方便阅读，长期运行所需的照料尽量少。[00:03:20]

他选择用 Python 脚本处理内容，再通过 Jinja2 模板生成静态 HTML 页面，部署到托管服务。这里的模板可以理解为预先写好的页面结构，程序把标题、正文等内容放进去，生成浏览器可以直接打开的文件。读者访问时，主要取得这些已经生成的页面，无需每次重新计算整份内容。[00:04:08]

这种方案与任务相配，是因为两个站主要交付信息。若产品需要多人实时编辑、复杂账号状态或实时交易，条件就发生了变化，合适的方案也可能不同。技术选择的理由，应当能够回到当前产品真正要做什么。

李自然提到，项目只使用了少量 Python 依赖。较少的依赖有助于减少一部分维护对象，但也意味着某些原本由框架提供的功能要自行安排：页面怎样生成、图片怎样处理、字体怎样加载，以及搜索引擎需要的页面信息怎样提供，都不能凭空省掉。[00:05:23]

所以，这个选择包含明确的交换。他愿意在早期把这些事情做清楚，换取自己更容易理解和掌握的结构。AI 能帮助写代码，却没有替他决定这种交换是否值得。所谓简单，仍然取决于项目需求和维护者能够理解哪些部分。

## 为什么中间结果尽量保留为能读懂的文件

自动内容站会经过许多处理步骤。如果某天文章出了问题，我们首先想知道，错误究竟在哪里出现：抓来的材料已经不完整，筛选时丢掉重要信息，还是写作时改变了含义？如果每一步都只在程序内部传递，定位起来会更困难。

这两个站尽量让中间输入输出使用 Markdown 文件。Markdown 是一种能直接阅读的纯文本格式，可以用简单标记表示标题、列表和链接。每篇文章保留为文件，最后再转换成 HTML。需要检查时，人可以打开相应文件，查看当时到底传了什么内容。[00:06:55]

可阅读的中间结果，增加了检查与恢复的机会。假如选题阶段已经选错，继续修改页面没有帮助；假如正文正确，只是页面排版出错，就不必重新生成全部文章。把处理步骤之间的内容保留下来，有助于缩小问题范围。

当然，纯文本也不会自动解决所有数据问题。需要精确字段的地方仍然要定义结构，哪些文件对应哪次运行也要明确。李自然的选择更适合围绕文章展开的工作：正文是人最需要检查的对象，让它保持可读，能减少一种重要的维护障碍。

## 阅读页的细节，来自具体判断

页面设计先由自然语言描述开始，再让 AI 生成一个初稿，随后逐项调整间距、链接、对齐和字号。李自然希望网站适合阅读，也希望它与常见的默认卡片式界面有所区别。因此，他没有把第一版样式当成已经完成的设计。[00:08:18]

字体选择体现了这种具体判断。中文采用带衬线的标题和不带衬线的正文，英文则采用相反的组合。这是他针对两个语言版本的审美选择，并不能推出所有网站都应该如此。读者实际感受到的是标题与正文怎样配合、阅读是否舒适，以及视觉是否符合内容的节奏。[00:09:04]

特殊字体还带来加载问题。完整字体可能包含大量页面根本用不到的字形，因此项目进行了字体子集化，即只保留需要的部分，减少下载负担。外观与性能在这里是相连的：一种字体再合适，如果读者每次打开页面都要等很久，体验仍然会受到影响。[00:09:19]

这些细节说明，使用自然语言编程并没有让产品判断消失。把“这里再大一点”“链接这样更容易辨认”“这组字体更适合中文”说清楚，本身就需要观察与比较。AI 降低了一部分实现成本，人仍然要知道准备往哪个方向修改。

## 页面后面，先让一条内容生产流程走完

两个站的大流程相近：取得材料，打分和筛选，确定要写的内容，完成文章，再生成页面并发布。新闻与论文的具体处理不同，但都需要把前一步的结果交给下一步。所谓自动化流程，就是把这些交接安排成可以重复执行的步骤。[00:10:32]

写作内部又分成编辑、写手和审核几项职责。编辑阅读已经评分的条目，选择哪些素材可以组成一篇内容，决定切入角度和篇幅；写手根据这些要求完成表达；审核再检查文章质量，需要时退回修改。[00:11:44]

| 工作阶段 | 主要接收什么 | 要作出的决定或产物 |
| --- | --- | --- |
| 编辑 | 已筛选和评分的材料 | 选题、材料组合、角度和篇幅 |
| 写作 | 明确的选题与相关材料 | 可以直接阅读的文章 |
| 审核 | 成稿及相应要求 | 是否通过，哪里需要修改 |

这种分工的作用，是把不同判断分别处理。选题要求我们比较许多材料，写作要求我们把已经选定的事情讲清楚；如果所有内容一直挤在同一段上下文里，表达可能受到大量无关材料干扰。分开以后，修改选题要求与修改文风也更容易分别进行。[00:12:19]

给几个调用起不同职位名，还不足以实现这种分工。真正需要明确的是各自看到什么、输出什么，以及后面怎样使用结果。同一个模型也可以在不同调用里承担不同职责，重点在任务安排，无需把它们想象成天然拥有不同专长的员工。

页面构建之后，还可能产生更新日志、公众号排版和邮件等内容。它们都依赖已经完成的文章，又有各自的格式要求。读者看到的站点很简洁，背后仍然可能有一条较长的生产流程。[00:12:43]

## 同一件新闻，怎样区分重复报道与新的进展

第一天，A 网站报道了一项新产品；第二天，B 网站也写了这项产品。如果我们的输入单位只是网页，就会看见两个不同地址、两篇不同文字。但对于已经读过昨天内容的人，今天再讲一遍同样的信息，可能没有多少帮助。[00:13:43]

这就是跨来源、跨日期去重的困难。我们需要比较的不只是哪篇网页已经抓过，还包括读者已经知道了什么。如果多个来源都在转述同一个发布消息，可以合并材料；如果隔天只是再次传播同样信息，就不必重新占据主要位置。

另一种情况是，同一产品出现了真正的新进展。假如后续发布了新的能力、结果或限制，那么它与昨天属于同一个主题，却仍然可能值得继续介绍。一见到相似主题就删除，会把这些变化一起过滤掉。[00:14:28]

因此，去重必须考虑内容含义。我们要区分“又有一篇文章谈同一件事”和“这件事本身发生了新的变化”。规则过松，读者每天看到重复；规则过严，重要更新消失。这一判断与产品承诺有关：资讯站希望让读者迅速知道新增的重要信息，不能只把新抓到的网页当成新增知识。

## 新闻要快，论文却可以故意等几天

材料取得的时间，也与内容类型有关。对于有投票或讨论的网站，刚发布时抓取，可能还看不到有用的社区反馈；过了较长时间，列表排序和关注焦点又可能变化。不同来源提供信息的方式与节奏不同，不能一律安排成相同的抓取时间。[00:14:56]

两个站因此采用了不同的节奏。资讯希望尽快让读者知道当天发生了什么，采用 T+0，也就是当天处理。论文简报则采用 T+3，等待约三天，再结合投票与反馈选择内容。李自然认为，对这个简报的读者而言，晚几天阅读论文可以接受，而多出的反馈有助于筛选。[00:15:34]

| 内容 | 采用的节奏 | 希望获得的价值 | 接受的代价 |
| --- | --- | --- | --- |
| 新闻资讯 | T+0，当天处理 | 及时知道重要变化 | 早期讨论和反馈可能有限 |
| 论文简报 | T+3，等待约三天 | 利用积累的社区关注与反馈 | 读到的内容晚于论文发布 |

这里的社区反馈是一种筛选信号，不能与研究质量完全等同。热门主题可能更容易获得关注，一些重要但小众的工作也可能暂时无人讨论。等待三天改善的是可观察的信息条件，并没有给出一个不会出错的论文评价器。

这也解释了为什么同一份代码换几个信息源，未必就能变成另一个好用的内容产品。不同领域对速度、重复、重要性和表达的要求都可能不同。可以复用抓取和生成的技术，仍然要重新理解新读者究竟需要什么。

## 让审核指出实际差距，写作才知道怎样修改

文章只生成一天，某种写法可能看起来很新鲜；连续阅读几天，读者就可能发现每篇都用同样的开头、转折和结尾。对于每天更新的产品，文风是否重复，需要放在多次交付之间观察，单篇质量检查不一定能发现。[00:17:04]

李自然为写作和审核持续调整了较详细的要求。其中一个核心做法，是提供具体反馈。文章过长时，先用 Python 计算实际字数，再明确告诉写作环节：现在有多少字，要求的范围是多少，必要时指出哪些部分应减少多少。这样，“太长了”就变成了可以对照的差距。[00:17:35]

模型并不擅长始终准确地估算自己输出的长度，程序计数可以承担这类确定性工作。模型继续负责怎样删改、哪些解释需要保留。两者结合，能够让修改更有方向；修改完成以后，还要重新检查实际结果，不能只接受模型说自己已经达到要求。

如果反馈始终很模糊，审核可能连续退回，文章却一直没有明显改善。自动流程会因此消耗更多时间，甚至困在循环里。因此，重写要有具体目标，也要限制尝试次数。超过限制以后，应当保留未通过状态，让系统知道这次没有完成。[00:18:16]

## 出错以后，哪些工作还能保留

自动运行要面对模型超时、网络请求失败、图片生成失败等情况。把所有失败都处理成“整天内容全部重来”，成本很高；把所有失败都忽略，又可能交付不完整或错误的结果。需要先判断，当前失败影响了什么。[00:18:51]

例如，站点中的一张辅助配图生成失败，文章可能仍然可以阅读，发布不必一直等待图片。某一篇文章的一个部分质量不足，也可以只重写对应部分，保留其他已通过内容。局部恢复减少了重复工作，也降低了重新生成时引入其他问题的机会。[00:19:04]

这个取舍要根据内容决定。对于文字已经讲清的资讯，少一张装饰性或辅助图片，可能仍然成立；如果任务必须解释一张实验结果图，缺图就可能影响主要内容，不能机械套用同一种做法。重要的是知道哪个结果是交付必需的，哪个可以暂时省略。

| 遇到的情况 | 可采用的处理方式 |
| --- | --- |
| 临时超时或请求失败 | 在有限预算内重试，仍失败就保留原因 |
| 非关键配图失败 | 保留有效正文，允许缺图发布 |
| 局部内容未通过审核 | 只重写受影响部分，再检查结果 |
| 任务被重复启动 | 用互斥措施避免同时写入同一份结果 |

日志同样要让人能读懂。只知道“任务失败”，很难恢复；知道哪一步、哪份材料、哪次请求出问题，才有机会接着已有结果继续。李自然还使用了文件锁等措施限制并发执行，避免两次任务同时改动同一个产物。[00:19:36]

## 输出格式也需要工程处理

有些步骤需要模型返回 JSON，也就是带字段和层次的数据格式。模型如果漏了引号、增加了不该出现的文字，后面的程序就可能无法读取。李自然在适合正文的地方尽量使用 Markdown，在仍需 JSON 的环节加入更有容错能力的解析。[00:20:00]

这项经验的重点，是承认输出格式可能失败，并为失败安排处理方式。反复要求模型“一定写对”，不能替代程序检查。不过，容错也必须有边界：可以修复清楚的格式问题，不能默默猜测一个不确定字段的含义，或把缺失的业务数据补成看似正常的结果。

格式修复与内容正确是两件事。一个 JSON 能解析，只说明程序能够读取它；里面的选题是否合理、文字是否准确，仍然要按任务要求检查。把这两层分开，才容易知道究竟需要重新请求模型，还是需要继续检查业务判断。

## 同一份英文材料，为什么采用两种双语写法

两个站都从英文材料开始，却没有使用完全相同的中英文生产方式。论文简报先写中文，再翻译成英文；新闻站则依据原始材料分别撰写中英文。区别来自内容的长度、表达目标，以及李自然对实际成稿的观察。[00:20:46]

在他的使用经验里，模型根据英文直接写英文时，较容易沿用材料的表达或陷入固定套路；写中文反而需要重新组织。这是对两个项目的观察，他提出的原因也属于解释性猜测，不能据此断言模型普遍更擅长中文。

论文简报相对短，英文版更重视忠实传达已经写清的内容，因此采用先写中文再翻译的方式。新闻对叙述与表达有更高要求，于是让两种语言分别从材料出发，形成各自适合阅读的文章。[00:21:49]

独立写作也有代价：两个版本的重点和细节可能不同，读者不能把它们当成逐句对应的译文。选择这种方式以后，就需要接受并管理差异，同时确保基本事实相容。双语产品到底更重视严格对应，还是分别获得自然表达，需要先作出选择。

## 留出表达空间，也保留明确的检查

最后，李自然提出一个面向未来的问题：如果提示词把所有步骤和表达方式都规定得非常死，模型能力提高以后，产品是否还能从中获益？他希望保留一些选择空间，让模型有机会使用更好的表达，同时用审核守住结果要求。[00:23:02]

写作风格是一个例子。提示词可以提供若干建议，但允许模型在有更合适方式时自行选择；同时要求避免与前几篇文章重复。审核再检查这次表达是否合适，如果重复或质量不足，就退回修改。自由发生在怎样写，检查关注读者最终得到什么。[00:23:54]

这种设计有机会减少不必要的束缚，但更换模型以后，仍然需要重新检查实际结果。更强的模型可能带来更好的表达，也可能改变篇幅、格式或成本。保留发挥空间，只是让改进有机会进入产品；持续验证才能知道改善是否真的发生。

## 总结提炼

两个内容站的难点，主要出现在连续交付之中。今天有一篇好文章还不够，明天要避免重复，后天要正确处理新进展；某个请求失败时，要知道哪些结果仍然有效，哪些必须停止交付。

静态页面与可阅读的中间文件，回应了个人项目的维护条件。编辑、写作和审核分工，让不同判断可以分别改进。新闻当天处理、论文延迟筛选，则体现了内容目标对自动流程的影响。

AI 可以承担大量实现工作，产品仍然需要清楚的判断：读者要获得什么，怎样知道结果合格，失败以后怎样恢复。理解这些具体关系，才有机会把一次成功的生成，变成能够长期使用的服务。

## 回看时的三个问题

同一产品连续两天出现在新闻里，什么时候属于重复，什么时候值得继续介绍？只比较标题或网页地址，分别会漏掉什么？

论文等待三天后再筛选，多获得了什么信息，又可能遗漏哪类内容？为什么这个选择不能直接照搬到所有资讯产品？

一篇文章的配图失败、某段文字未通过审核、整个任务被重复启动，这三种情况应该怎样分别处理？哪些已完成工作可以保留下来？
