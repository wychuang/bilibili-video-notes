# 把 AI agent 的手工验收改成可重复的回归测试

## 写代码之外，时间花在反复确认结果

数字黑魔法回顾自己开发 AI agent 的时间时，估计写代码和做设计只占约 10%，其余约 90% 用在手动测试：打开网页、输入测试数据、盯着 agent 逐步运行，再靠人判断结果有没有变好。只改一条 prompt，也可能让整个流程表现不同；结果不稳定时，他就得一遍遍重跑。[00:00:00]

他把这个问题归结为“生成容易，验证昂贵”：agent 的回答是一段自然语言和一串执行步骤，很难像普通函数那样只拿一个数字判定对错。芯片设计与验证提供了一个参照：芯片出错后修复代价很高，因此行业会设计回归测试、检查点和覆盖率指标，反复寻找问题。作者想把类似的验证习惯用于 agent，让每次改动都能被检查。[00:01:24]

## 先让另一个 agent 看得见系统

第一步是把被测 agent 改造成更容易由另一个 AI 工具检查的系统。作者手里有一套自己写的 agent，以及一套用于写代码的 coding agent，例如 Codex。原系统入口只有网页界面，运行中的调用链和中间数据留在 UI 里；离开页面后，测试过程就难以继续或复盘。[00:04:04]

作者提出两条路：让另一个 agent 通过 MCP 模拟网页操作，或把前后端拆开，让后端能够独立运行、通过命令行调用，前端只负责显示状态和供人操作。他选择了后端独立运行的方式，理由是这套系统需要处理授权、边缘情况和效率问题；他说自己在 Vercel AI SDK 上也花了不少功夫，才把后台运行方式整理好。[00:05:38]

要让 coding agent 检查流程，系统需要留下它能读取的材料：整条 workflow 的步骤、每一步调用的工具、返回的数据和中间状态，并提供接口让它主动获取。作者援引 SWE-agent 研究中的 Agent-Computer Interface（ACI）概念，强调 agent 也需要为它设计的操作接口。接口能不能把必要信息明确交给 agent，会影响它完成任务的表现。[00:06:54]

## 用两层裁判处理确定和模糊的结果

回归测试先为新功能定义 happy path，也就是预期的正常工作路径：什么条件下触发工具，之后的流程怎样推进。然后把验收拆成两层。[00:07:43]

第一层是确定性的断言，检查工具是否触发、中间记录数量是否符合预期，以及测试覆盖了哪些情况。这些规则适合判定清楚的事实。第二层是 LLM supervisor，专门评估难以用固定规则判断的输出。作者要求 supervisor 使用干净的上下文，只看到评估标准和待评结果，不参与开发；面对没有标准答案的自然语言输出，让它按尺度打分，比较效果变化。[00:08:21]

[[FRAME:00:08:15|检查技能时分别看工具是否触发、参数是否提取正确，以及结构是否符合约定。]]

测试案例来自两处：一类是开发新功能时写下的 happy path；另一类从真实用户输入和测试中收集，补上团队起初没想到的情况。作者还给每个新功能配一个 feature flag，让同一组回归案例分别在功能开启和关闭时运行，以观察新功能带来哪些改善、又影响了哪些原有表现。[00:10:02]

## 让 coding agent 根据测试结果继续修改

有了可读的运行记录和测试集之后，coding agent 的工作顺序也随之改变：先为新功能设计回归测试和开关，再编写代码；之后在开关两种状态下执行同一套测试，读取反馈并继续调整，直到结果符合验收要求。[00:11:01]

这样，人需要先明确“什么算对”，自动化流程才能反复检查改动。验收标准写得过宽，错误答案可能轻易过关；标准遗漏某种输入，测试全部通过也可能仍有问题。因此需要结合真实失败案例，继续补充测试并检查评分是否合理。[00:11:44]

这套思路的重点不在某个特定框架，而在于找出项目里重复、耗时又能被定义标准的验证工作。先把执行路径和中间状态留下，再把能明确判断的条件写成断言，把主观判断转成有标准的评估，最后用真实案例持续补齐回归集。[00:12:24]

## 总结提炼

作者把 agent 开发中的手工验收拆成可读接口、确定性断言、LLM 评分、持续积累的案例和 feature flag 对照，再交给 coding agent 按测试结果迭代代码。约 90% 是他的个人时间估计，视频呈现的是架构思路与工作流。
