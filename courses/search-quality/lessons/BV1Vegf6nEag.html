记得住、找得回、用得对：Agent 记忆与系统评测

来源：吴恩达Agents 上传的 18 集合集 · 合计约 3 小时 33 分钟 · 全集主线导读。P01–P07 是与 Oracle 合作的 Agent 记忆课程；P08–P18 转入另一门聊天系统课程。以下按实际内容分组，上传标题中的评价性宣传不作质量依据。

一句话抓住核心

记忆负责把过去变成当前可用的信息，评测负责检查这些信息有没有让任务完成得更可靠。

P04 工具箱检索；避免一次塞入全部工具说明

一、用户说“订第一家”，系统为什么听不懂

第一轮问附近餐厅，第二轮说“帮我订第一家”。无状态系统只看第二句话，不知道“第一家”指什么；保存并取回上一轮推荐后，系统才能继续询问日期和人数。[P02 00:01:45]

这是最小的记忆价值：保留关系，让后续行动有依据。真正预订前仍需确认必要信息和授权，记忆不能替代用户决定。

保存聊天记录只是起点。任务可能跨越多个会话，记录越来越长；重要事实埋在闲聊里，反复发送完整历史既贵，也未必容易找到关键内容。

二、不同信息，值得不同保存方式

课程区分对话、知识库、工作流、实体、摘要与工具信息，并通过记忆管理器统一读写。[P03 00:02:00]

记忆内容 典型问题 保存时的重要字段
对话记录 上一轮指的是哪篇论文？ 会话、角色、时间、原文
知识资料 这篇论文说了什么？ 来源、版本、片段、检索表示
工作流经验 上次怎样完成这个任务？ 目标、有序步骤、结果、适用条件
实体信息 当前讨论的是谁或什么？ 实体标识、关系、来源
摘要与索引 长历史中有哪些相关内容？ 摘要、原文位置、关联 ID
工具目录 当前问题能用哪个工具？ 用途、参数、限制、执行入口

课程使用 Oracle 数据库，方法不限定某个供应商。也不要求每种信息都做向量搜索：确定的 ID、时间与权限通常适合精确查询，模糊语义才需要相应检索策略。

“存进数据库”只是写入成功；能否找回、找回后是否用对，需要另外测试。

三、工具多了，可以先检索工具

如果有几百个工具，把所有名称、参数和说明都放进上下文，可能挤占任务信息。课程把工具说明存起来，根据当前问题先找出相关工具，再供模型选择。[P04 00:00:00]

以“查一篇论文”为例，系统可以先找到论文检索工具，再决定参数；需要保存全文时，再找到相应摄入工具。视频还尝试用模型补充工具描述，帮助区分相似工具。[P04 00:09:00]

这里会增加一道新关卡：工具检索遗漏了正确工具，后续模型就没有选择机会。增强描述也可能夸大能力，因此应与真实函数签名和行为核对，不能让模型随意改写执行事实。

四、摘要会丢信息，原文索引让它有机会补回来

课程把两种操作分开：一是把长历史写成短摘要；二是把内容放到外部存储，在当前上下文留下描述和 ID，需要时展开。[P05 00:02:10]

摘要便于继续任务，但始终有信息损失。外部存储能保留原文，却也需要可靠检索。只剩一个 ID，而系统不知道何时读取，同样帮不上忙。

演示中，会记录哪些消息已经被摘要，避免重复处理；通过关联 ID 找回原始记录。评测时应检查摘要是否保留具体约束、未解决问题和来源位置，而非只看压缩比例。[P05 00:13:20]

视频按字符估算 token，并用使用率阈值触发压缩。这些是教学设置。实际系统应使用对应模型的计数方法与预算，中文字符不能照搬英文的“每四个字符一个 token”。

五、记忆操作可以由程序决定，也可以交给 Agent

程序可以在每次任务开始时读会话、结束时存结果，并在预算触限时触发处理。Agent 也可以按需要调用“查记忆”“展开摘要”等工具。[P06 00:02:25]

确定性规则负责必须完成的底线，模型决定较灵活的信息获取。删除、覆盖、长期保存私人偏好等操作，还应受单独权限与保留规则约束。

课程最终用论文研究串起完整过程：[P06 00:12:15]

  1. 找 MemGPT 论文，取回候选。
  2. 用户继续说“保存论文”，系统通过对话记忆识别对象。
  3. 再问主要内容，从已有资料中组织回答。
  4. 摘要历史后，追问第一个问题，系统展开关联记录再回答。

这一连串操作比一次问答更能测试连续性。但保存输出、复用流程与更新模型参数是不同机制，不能统称为模型已自动学会新能力。

六、第二门课：先把客服的状态讲清楚

P08 开始转入聊天系统课程，例子是电子产品客服。主流程是识别输入、找产品信息、生成回答、检查输出，再把结果交给用户。[P08 00:00:00]

分类会影响后续路径。删除账号与了解电视，所需资料和允许操作不同。结构化分类结果便于程序使用，但还需要校验字段，并处理混合意图和未知类别。[P10 00:00:35]

P09 的字母反转例子说明 token 与字母不总是一一对应；其中模型名称、上下文长度和 API 用法属于早期版本示例。本篇保留原理，不把旧参数当现行配置。[P09 00:06:20]

七、检查问题中的假设，再组织回答

用户问“某 Chromebook 比某台式机贵多少”，产品资料却显示前者更便宜。系统应先核对前提，不能顺着“更贵”这个措辞编一个差价。[P12 00:04:10]

P13 把流程拆开：提取产品或类别，查询相应目录，再生成答复。查不到路由器就返回空集合；用户只问电视类别，就查该类别，而无需加载全部商品。[P13 00:03:15]

拆步的意义是让状态与错误位置清楚，也便于插入工具和人工检查。它可能增加调用与延迟，是否值得要按任务测量。教学代码中用字符串替换修补 JSON 的方式也较脆弱，生产系统应严格解析和校验结构。

八、审核、事实检查、注入防护是三件事

P11 演示内容审核与冲突指令检测，P14 演示回答是否符合产品资料。[P11 00:00:04] [P14 00:01:55]

内容通过审核，不代表事实正确；事实来自资料，也不代表满足用户需求。分隔符有助于区分输入段落，但不能提供可靠安全边界。网页和检索片段里的指令也应当作不可信数据处理。

增加一个模型来检查输出，是一种可尝试的质量控制方式，同样会出错，也会增加成本。需要用真实错误样本校准，避免两个模型一致犯错。

九、从一个失败样本长出评测集

P16 先用少量例子试运行，发现输出多了无关文字后，把失败问题加入开发集，再调整提示。修改后重跑原有例子，避免修好一处又破坏另一处。[P16 00:08:55]

随后，用明确的产品列表作为预期输出，自动判断类别和产品是否匹配。十个例子能帮助快速发现回归，却不足以支持细小百分比差异的稳定结论。[P16 00:12:25]

反复用来调整系统的数据属于开发集。要估计泛化表现，还需要有代表性的保留测试数据。高风险场景不能因为原型方便，就跳过上线前验证。

十、开放回答怎样打分

P17 面对多个都可能合理的客服答复，转向 Rubric：是否回答问题、是否忠于资料、是否加入无依据内容、是否与资料冲突。[P17 00:00:35]

有专家参考答案时，可以比较事实覆盖，而无需逐字一致。比参考答案短，可能遗漏要点，也可能更简洁；比参考答案长，可能补充有用内容，也可能编造。必须继续看内容，不能用长度直接决定好坏。

迁移练习：测“记忆”时故意改变一点点

设计五组低风险对话：跨轮指代、换会话继续、用户修正旧信息、相似名字区分、删除后不再使用。每组写出应保留与应遗忘的内容，并记录实际调用。

再检查三个指标：该用的记忆是否找回；不该用的信息是否被隔离；回答有没有正确应用记忆。特别留意旧偏好覆盖新要求、不同用户数据串用、错误答案被再次存成事实。

这份练习把记忆工程与质量评测连接起来：系统可以保存很多内容，最终仍要看是否改善了具体任务。
