给 Agent 一个工作间，也给它一道边界

来源：AI大模型元元 · AI Agent 的沙盒是什么 · 17 分钟 · 批判性快读。原视频有较多绝对化描述，本篇将可用框架与未证实的宣传判断分开。

一句话抓住核心

让 Agent 操作文件与网络时，需要隔离环境、限制权限、控制资源，并保留能追溯的执行记录。

从“说错”到“做错”，损失会变化

聊天模型给出错误建议，人还有机会识别。Agent 若获得文件写入、代码执行与联网能力，错误就可能直接变成文件损坏、信息外传或持续的调用费用。[00:00:10]

因此不能只在提示词里写“请注意安全”。系统要实际限制它能看见什么、能修改什么、能访问哪些外部服务，以及最多运行多久。

四块能力，要分别验收

能力 一个具体问题
隔离 任务能否访问工作目录之外的私人文件？
授权 读文件与发送文件是否需要不同权限？
资源限制 死循环时能否停止，并控制 CPU、内存和调用次数？
状态与记录 哪次工具调用改了什么，能恢复到哪里？

这是视频后半段架构的实用提炼。不同产品可能把这些职责放在不同组件里，不能因为名字叫“沙箱”就推定四项齐全。[00:08:30] [00:12:00]

快照恢复有清楚的边界

视频用“时光机”比喻回滚。对本地文件或进程状态，这有直观帮助；已经发出的邮件、已经提交的支付、外部系统收到的数据，却不会随本地快照自动撤回。

因此有外部影响的动作仍要在执行前确认，并设计幂等、防重复提交和补偿流程。日志也需要脱敏，不能为了便于排查就长期保存全部机密输入。

不同隔离技术，不应混成一种魔法

原视频把 Firecracker、gVisor 等技术放进同一条叙事，但它们的机制不同：Firecracker 面向轻量微虚拟机；gVisor 提供用户态应用内核式隔离。它们都要结合配置、权限和更新来评估，不能用“彻底防逃逸”概括安全保证。Firecracker 官方说明 · gVisor 架构说明

视频里的“所有环境毫秒级回滚”“风险归零”“没有沙箱就无法合规”等说法缺少适用条件，本文不采用。法规结论需要具体法域和场景核对，不能从产品讲解直接推出。[00:08:00] [00:12:50]

迁移练习：给一个任务画权限边界

以“读取三份报告并生成摘要”为例，明确输入目录只读、输出目录可写、是否允许联网、最大运行时间、哪些操作必须确认。

再设计三个无害测试：尝试读一个未授权的测试目录；模拟网络失败；让任务超过预算。记录系统是否清楚说明被拦截的原因。所有测试都在专用样本环境中完成，避免拿真实私人文件做试验。

这条视频适合帮助列出问题。真正选择隔离方案时，应继续查对应实现的威胁模型与限制。
