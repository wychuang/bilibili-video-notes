## 从可执行文件开始

我们可以先区分两种东西：源代码是人写的程序文本，可执行文件则是编译器把程序变成机器指令后交给电脑运行的文件。拿一个只做加法的 C 小程序举例，编译后会得到 `a.out`。运行它能看到计算结果，但直接打开文件读不到原来的代码，因为里面保存的内容已经不是那份源代码文本。[00:00:51]

这正是逆向工程要处理的问题：从可执行文件等已有产物出发，分析它的结构和行为，尽量还原程序的逻辑。上传者把源代码删掉后，让带有 REA 技能的 agent 分析 `a.out`，并生成一个 C 文件。第一次检查时，恢复出的代码和原来的小程序相同，看起来像是把源代码找回来了。[00:01:16]

## 逆向工具提供材料，模型负责解释

要看 agent 怎样做出结果，可以查看它的工具调用。先调用 `open binary` 获取文件类型信息；这一类信息通常可以由系统的 `file` 命令读取，例如文件适用的操作系统、位数和指令集。之后，agent 调用函数分析工具，取得函数信息与汇编指令。汇编是更接近处理器指令的文本，能帮助逆向人员理解程序在执行什么。[00:01:36]

这里的关键发现是：核心分析来自已有的逆向工具。图形界面里可以同时看到机器指令和反编译生成的 C 风格伪代码；agent 通过 REA 技能获知哪些工具可用、遇到什么任务该调用什么工具。REA 还提供 MCP 和命令行接口，让 agent 能把工具接进工作流。它组织了工具的使用说明与调用入口，实际分析依然依赖本地安装的逆向程序。[00:02:17]

反编译结果也不等于原始源代码。上传者改了变量名，还加进一些不起作用的代码，再次编译后重新分析。生成的文件仍出现了 `ab_result` 这样的常见变量名，却无法复原他新设的名称。二进制文件通常没有保留原来全部变量名；模型是依据反编译结果猜测适合的名字。最初看起来“完全还原”的结果，部分来自示例程序采用了模型熟悉的常见命名。[00:02:42]

这个测试说明两件事要分开看：逆向工具提供了能继续分析的结构与伪代码，语言模型则能根据这些线索解释程序，并补上人类熟悉的命名。原始名字和注释等源代码信息若没有保存在二进制文件里，模型不能凭空从文件中读回来。[00:03:08]

## 使用技能也要安装本地工具

REA 的工作方式离不开本地依赖。上传者描述首次使用时，技能在项目的隐藏工具目录中安装了逆向软件，还下载了运行它所需的 JDK。工具被放在项目自己的目录里，其他项目未必能直接复用；因此，使用体验除了模型调用，还包括本机安装、占用空间和管理这些依赖。[00:03:57]

这也解释了为什么查看工具调用记录有帮助：光看 agent 输出的 C 文件，我们可能会误以为 REA 自己完成了全部逆向。检查调用链后，才能看清哪些结果来自系统文件识别命令、哪些来自反编译工具、哪些是模型根据结果作出的解释。对 agent 项目而言，选择什么工具、何时调用以及怎样呈现结果，会直接影响使用者对能力和成本的判断。[00:04:19]

## 项目热度与软件逆向的意义

上传者认为，REA 的价值首先是让更多人注意到 AI 可以参与软件逆向。他也把 Blender、数学自动化等例子放在一起，提醒观众：AI 项目走红，有时会让人看见已经存在多年的工具和研究方向。理解其背后的技术路线，比只追逐每个新项目更有帮助。[00:04:21]

他对 REA 本身的未来潜力持保留态度：agent 即使没有这套技能，也可能自行选择合适的逆向工具；若一次加载大量工具说明，反而会占用上下文，限制模型选择其他方法。这是上传者对项目设计的判断。另一方面，他也认为 AI 让普通人更容易尝试逆向，可能降低一些闭源软件原有的保护门槛。这是对行业后续变化的个人预测，演示中的一个简单程序并不能证明商业软件都能被轻易复制。[00:04:51]

因此，看这类工具时可以沿着三层问题往下拆：目标文件是什么、工具实际分析出了什么、模型又在这些结果上推断了什么。把三层分清，就能知道一个“逆向成功”的示例到底恢复了哪些程序逻辑，哪些细节仍只是猜测，也更容易判断 AI 和传统工具各自贡献了什么。[00:06:01]

## 总结提炼

REA 通过技能说明、MCP 和 CLI 把本地逆向工具接给 agent。`file` 一类工具识别可执行文件，反编译工具提供汇编与伪代码，模型再据此解释程序。简单测试能恢复主要逻辑，却不能找回二进制文件未保留的原始变量名；所谓商业软件护城河变化仍是上传者的判断与预测。
