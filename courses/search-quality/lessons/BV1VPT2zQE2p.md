# 工具调用怎样变可靠：让模型知道选什么，也让程序接得住

> 来源：从4个方面，速通15个Agent工具调用技巧  
> UP 主：费曼学徒冬瓜 · 7 分 18 秒 · 深度阅读  
> 链接：https://www.bilibili.com/video/BV1VPT2zQE2p/

我们让一个出行助手帮忙安排行程。它可能需要先查天气、看地图，再根据已经确定的计划处理订票或酒店预订。对人来说，这些动作的先后和用途容易理解；对模型来说，系统必须先告诉它有哪些工具、每个工具做什么、需要哪些信息。模型再根据用户的话，选择工具并写出调用指令。真正查询天气或提交订单的工作，由接到指令的程序执行。

所以，一次工具调用至少包含两个需要分别做对的判断：选对工具，填对参数。即使模型选中了查天气的工具，如果城市或日期填错，程序也可能正常执行，却返回与用户无关的结果。反过来，参数格式写得再规范，选错了工具也不能完成任务。理解这条最基本的过程，才知道后面的优化究竟在帮助哪一步。[00:00:00]

## 先把工具设计成容易理解的工作

第一件事是控制模型眼前需要选择的工具数量。如果每次都把大量功能相近、描述重叠的工具交给模型，模型就需要花更多精力区分它们。出行场景提供了一个可理解的拆分：规划阶段主要用查天气、查地图等工具；执行阶段才涉及订票、订酒店。把职责分开，可以减少每个环节需要面对的选择。具体用一个助手分阶段加载，还是采用多个助手分工，仍需结合系统设计，工具多并不自动意味着必须拆成多 Agent。[00:00:32]

关于工具数量，常见建议会给出不同的经验范围。它们适合提醒我们关注选择难度，不能当成脱离任务和模型能力的统一上限。十个用途清晰、差异明显的工具，和十个名字相似、职责重叠的工具，带来的困难并不相同。需要观察的是，模型能否根据用户的问题稳定找到合适工具，以及增加工具以后错误有没有变多。

第二件事是让一个工具承担清楚的职责。例如，不要把查天气和订酒店混进一个意义模糊的大函数。模型看到工具名字和说明时，应当能够理解调用之后会发生什么；后端程序也应当能解释这次调用完成的是哪件事。职责越含糊，模型越需要猜测内部的分支和条件，出了错也越难知道是选择的问题，还是执行的问题。[00:01:12]

第三件事是减少不必要的参数。有些信息系统本来就知道，例如当前是哪位登录用户，或者某项已经保存在数据库里的资料。让模型再次从自然语言中猜一个用户标识，既增加错误机会，也重复了程序已经能完成的工作。可以由程序在授权范围内补入这些已知参数，让模型只处理确实需要从用户需求里理解的部分。这样简化的是模型的判断任务，后端仍然要清楚知道每个参数来自哪里。[00:01:24]

还有些短小、经常用到的信息，可以提前准备，减少一次专门的工具调用。个性化推荐是这里的例子：如果某个必要属性已经在当前任务的使用范围内，程序可以先查出并放入上下文，模型无需先发起一次查询才继续回答。不过，信息少并不代表可以无条件提供。与当前任务无关的个人属性，不宜因为“可能有用”就一并交给模型；是否提前准备，要同时考虑必要性和用户授权。[00:01:45]

最后，即便接口已经尽量简单，后端仍然需要校验。模型可能遗漏必填项、填写不允许的取值，或把参数写成错误类型。像 Pydantic 这样的数据校验库，可以帮助程序检查输入是否符合定义。发现错误以后，应当让模型知道具体哪里不合要求，再生成新的调用参数。这里需要修复的是已经识别的错误；程序无法确认用户意图时，不能为了让调用通过而随意补一个值。[00:02:06]

## 给工具写一份真的能用的说明

工具定义可以看作模型使用程序时的说明书。名字、用途、适用时机、输入参数、返回内容，都需要足够清楚。只写“用于查询信息”，模型仍然不知道能查什么、什么时候该用、结果是什么形态。参数也一样：一个字段是否必填，允许哪些取值，代表用户的哪个需求，都应当在模型作决定之前说明。检查说明是否清楚时，可以先问自己：只读这些内容，能否判断一次调用会做什么？如果人还需要猜，模型通常也会遇到同样的歧义。[00:02:45]

调用格式则解决程序如何接收的问题。约定使用 JSON 等结构化格式后，后端才能按固定方式解析工具名称和参数。结构化输出让程序更容易读懂指令，但它没有保证指令的含义正确。城市名称放在正确字段里，并不表示那座城市就是用户想查的地方。因此，格式校验与任务理解都需要检查，不能因为 JSON 解析成功就宣布这次调用正确。[00:03:09]

说明文字之外，具体示例也很有用。给模型看一个用户问题，以及对应的正确工具和参数，它就能看到抽象规则怎样用在实际语言上。这类在提示中提供少量例子的做法，通常叫 few-shot。还可以从历史记录中检索与当前问题相近的成功调用，让模型参考类似情境下怎样做选择。检索增强在这里提供的是调用案例，而非直接提供问题的答案。[00:03:31]

例子需要和当前任务相近，也要有正确性保障。如果把一个偶然成功、实际含义却不匹配的调用当成示范，模型可能重复同样的误解。历史记录还可能包含个人信息，作为示例使用前应当去掉与解释调用方式无关的敏感内容。保留下来的重点，是问题表达、工具选择和参数之间的关系，让模型能学会这种关系，而非照抄某个真实用户的数据。

当运行中出现反复发生的错误，可以进一步补充使用规则。例如，模型总是漏掉某个必填字段，就把字段要求写得更明确，并配一个容易误解的例子；模型常把调用结果当作已经执行完成，也需要说明不同返回状态分别意味着什么。规则应当对应真实错误，写清需要采取的动作。不断增加口号式强调，未必能帮助模型理解到底错在哪里。[00:03:54]

有时问题出在用户表达本身。提问中可能混有背景、多个目标和省略的条件，导致模型选错工具。可以先整理问题，提取关键需求、明确已有信息，再把更清楚的任务交给调用环节。问题改写要保留用户的真实意思；如果条件确实缺失，改写不能凭空造出条件。这里的目的是让已有意图更容易理解，必要时仍然需要用户补充。[00:04:11]

## 模型是否擅长工具调用，要在实际问题上看

工具和说明写好以后，还需要选一个能理解它们的模型。支持 Function Calling 的模型通常具备专门生成结构化调用的能力，可以作为候选。但“支持某项能力”和“在我们的工具上表现可靠”是两件需要分别确认的事。一个模型可能很会输出合法格式，却在几个相近工具之间选错；也可能选对工具，却不能从用户的复杂表述中提取完整参数。[00:04:42]

因此，应当用实际场景的问题测试候选模型。尤其在企业环境里，可用模型可能只有平台已经部署的几种，选择范围本来就有限。此时更需要比较它们在相同工具和问题上的表现，知道哪一类任务做得好、哪一类容易失败。不能只根据模型名气，推断它会熟悉我们自行定义的工具。

有条件时，还可以针对工具调用做微调。训练样本把用户可能提出的问题，与正确的工具调用指令配成一对，让模型学习任务表达怎样对应具体工具和参数。这里最重要的是样本真的代表实际场景，调用结果也正确。如果训练数据重复了原有歧义，模型只是更熟练地重复不可靠的模式。微调有成本，也需要评价，适合在已有测试指出明确问题之后考虑。[00:05:33]

## 记录完整的一次调用，才能知道该改哪一处

上线前准备测试集，至少分别检查工具选择和参数生成是否正确。两种错误的修复办法可能不同：工具选错，可能是职责划分或说明不清；工具选对但参数错误，可能是参数定义、示例或问题理解出了问题。如果只统计最后有没有返回一段文字，许多调用错误会被看起来正常的回答遮住。[00:06:02]

| 观察到的情况 | 还需要看什么 | 可能优先检查的位置 |
| --- | --- | --- |
| 选择了不相关的工具 | 用户意图是否清楚，工具描述是否重叠 | 工具职责与适用条件 |
| 工具选对，参数不对 | 缺少字段、类型错误，还是含义理解错误 | 参数说明、示例与校验反馈 |
| 调用被程序接受，却没完成任务 | 工具执行状态与返回结果 | 后端执行及对结果的解释 |
| 换一类问题后表现下降 | 新问题和测试样本有什么差别 | 测试覆盖与调用案例 |

上线后继续记录用户问题、模型输出的调用指令和工具执行结果，这三部分连起来，才形成一次可解释的调用。如果日志只写“失败”，我们无法知道模型有没有选对工具；如果只记录模型输出，也无法判断程序是否真的执行成功。日志需要在保护敏感信息的前提下保存足够上下文，让后续分析能回到实际发生的事情。[00:06:17]

分析日志后，改动才更有方向。一个工具经常填错参数，可以先修改说明或补充调用示例；某个工具长期很少被使用，则可以检查它是否确实多余，或是否被另一个描述过宽的工具抢走了用途。调用频率只是线索，低频也可能对应少见却重要的任务。确认它承担什么职责之后，再决定是否减少工具数量，比只按使用次数删减更稳妥。[00:06:29]

## 总结提炼

可靠的工具调用由一连串明确的交接组成：用户提出需求，模型根据说明选工具、填参数，后端检查并执行，再把真实结果交回。优化可以沿着这条过程逐步进行，先减少工具和参数中的歧义，再用示例帮助理解，最后用测试和日志观察实际行为。

这也解释了为什么单独改提示词往往不够。模型需要清楚的接口，程序需要可解析且经过检查的参数，开发者需要看得到每一步发生了什么。只有把错误定位到具体环节，下一次修改才知道是在解决哪一个问题。

## 回看时的两个问题

一次调用输出了合法 JSON，也成功返回了结果，为什么仍然可能没有完成用户的任务？把工具选择、参数含义和执行结果分别解释清楚，就能看见其中的差别。

如果模型总是填错一个参数，哪些信息可以让你判断应该改说明、改示例，还是让后端直接提供这个值？回到具体调用记录，比笼统地说“模型不够聪明”更有帮助。
