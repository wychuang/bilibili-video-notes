# MCP 与自研插件：企业接入工具时的四类取舍

> **来源**：AI大模型-阿水，《AI界USB火了一年，大厂为何偏要砸钱手写插件？》，4:21，https://www.bilibili.com/video/BV1RxWE66E2D/  
> **阅读强度**：quick

模型上下文协议（MCP）用统一方式描述模型如何调用外部数据和工具，降低了模型与工具之间的接入成本。对权限、速度和业务流程要求更高的系统，还要考虑工具接入后的实际表现。作者用四类顾虑解释企业为什么会自研部分插件；这些是特定业务场景里的取舍。

第一类顾虑是权限与数据安全。金融或医疗系统可能需要把访问权限细分到某一行、某个字段，还要和企业身份系统对应。若工具调用时无法确认请求最终来自哪位用户，就可能让权限较低的人读到不该看到的数据，例如实习生查到高管工资单。自研插件可以把用户身份或会话信息带到内部调用链，在访问底层接口前检查权限并处理敏感数据。具体能否做到，仍取决于插件如何实现和接入企业的身份系统。[00:00:41]

第二类是延迟。在一个多步骤任务里，模型可能先检索，再分析结果，再调用下一个工具。若每一步都要经过客户端与服务端通信，还要序列化、传输和解析数据，反复调用就会累计网络开销；并发增加时，服务端还可能排队。自研插件可以选择本地函数调用，或通过 gRPC（一种服务间通信协议）直连内部业务系统，以缩短关键路径。实际速度仍取决于部署、网络和服务负载。[00:01:27]

第三类是需要等待和恢复的长流程。报销审批不仅要查资料，还可能发起异步任务、等待系统回调，并在主管确认前暂停。单次请求与响应的交互方式不容易单独表达整条流程的状态；插件若直接接入企业工作流引擎，就可以复用已有的异步事件、状态管理和恢复机制。系统要记住任务进行到哪一步、等待谁的动作，以及确认后从哪里继续。[00:02:08]

第四类是遗留系统。企业内部可能还在运行多年前建成的 SOAP 服务接口、私有 TCP 网络协议，甚至直接连接硬件的指令。把所有接口都包装成统一格式会增加开发工作，也可能丢掉批量处理或事务控制等原有特性。自研插件可以写适配代码，用更贴近旧系统的方式调用。事务控制是让一组相关操作一起成功或一起撤销的机制；若把这层能力简化成普通的一问一答，业务结果就可能不完整。[00:02:50]

这几类问题可以通过组合架构处理。天气查询、网页搜索、基础文档解析等通用且低敏感的任务，可以使用现成 MCP 工具，节省接入时间；涉及核心交易数据、精细权限或复杂流程的任务，则考虑自研插件。企业还可以通过 API 网关（统一接收和转发模型工具调用的入口）管理内部插件，并按需要把部分能力包装成 MCP 服务。这样既保留了通用协议的互操作性，也允许关键业务调用保留定制的权限与流程。[00:03:23]

## 总结提炼

MCP 主要降低工具接入的统一成本；自研插件可以更贴近特定系统的身份权限、调用性能、长流程状态和遗留接口。四类取舍分别落在谁能访问、调用要花多久、任务怎样等待恢复，以及旧系统能力如何保留。常见的折中方式是按业务敏感度和流程复杂度选择工具，并在统一网关下管理需要定制的能力。
