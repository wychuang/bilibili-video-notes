# Agent 要动手：先选接口，再设计失手之后怎么办

> 来源：[左右横眺｜关于 Agent、GUI 与 API 的产品讨论](https://www.bilibili.com/video/BV16V6iY3EJj/)；全片约 19 分钟。产品演示与预测具有录制时间背景，本文保留能迁移的分析方法。

## 一句话抓住核心

Agent 完成任务，需要把模型的意图变成受约束、可观察、可恢复的操作；会点击按钮只是其中一环。

## 一次“调用工具”，到底是谁在执行？

我说“查一下订单”。模型可以生成一个结构化请求：调用查单函数，参数是某个订单号。真正读取数据库、检查权限、返回结果的是宿主程序。模型提出动作，运行程序执行动作，二者需要分开理解。[00:01:45]

另一条路线是操作界面：观察截图或页面结构，再点击、输入、滚动。它接近人使用电脑的过程，能够接触很多没有专用接口的任务。[00:02:50]

这两条路线各有成本。结构化接口通常更容易验证参数和结果，但覆盖范围由接口决定；界面操作能利用现有软件，却容易受到弹窗、布局变化和识别错误影响。[00:06:40] [00:10:20]

## 能拿到结构化信息，就别只猜屏幕

视频提到一种务实方向：把 API、页面结构与视觉观察结合起来。界面元素能提供明确的文字或标识时，可以利用这些信息；确实依赖画面的任务，再观察图像。[00:09:30] [00:11:20]

例如查找报表，可以通过稳定接口获取列表，再让用户在界面里确认下载对象。无需为了显得“像人在操作”，把一个可靠调用拆成十几次鼠标点击。

操作方式也不改变权限边界。GUI 只能在用户已有、明确授予的访问范围内行动；登录、验证码、支付确认与平台限制依然需要被尊重。这里是对执行边界的补充说明。

## 真正拉开体验差距的，是出错之后

视频借用 RPA 的经验提醒：自动化要考虑日志、可靠性、隐私以及异常处理。[00:12:15]

把这句话落成三个测试就很具体：

| 测试情境 | 我需要看见的行为 |
| --- | --- |
| 查订单接口返回 404 | 解释未找到，核对对象，不编造订单状态 |
| 点击前出现了新弹窗 | 重新观察页面，不沿用失效坐标继续点 |
| 提交后网络中断 | 先查是否已经成功，避免重复下单或发送 |

以上是迁移测试，视频没有提供这三项的实测数据。它们帮助我把“Agent 不稳定”拆成可以复现的问题。

对会发消息、改文件、花钱的动作，还应有适当确认、最小权限和可追溯记录。失败后能否恢复原状，需要按具体工具设计，不能仅靠一句提示词保证。

## 迁移练习：给一个动作写验收标准

挑选一个低风险任务，例如“从公开网页找出三篇相关文章，存成草稿”。写出允许访问的范围、完成产物、失败信号和停止条件。

验收时统计任务是否完成、引用是否正确、是否越权、是否出现重复操作。点击次数和思考长度只作为过程信息，不能直接充当完成质量。
