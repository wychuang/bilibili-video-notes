# 两个月的 Agent 自学复盘：从业务场景走到可测试系统

> **来源**：程序员海豚吞，《自学两个月Agent，复盘思考》，6:19，https://www.bilibili.com/video/BV1WpbW62Eg3/  
> **阅读强度**：quick

一个 AI 面试系统可以从一条用户消息开始：系统读到消息后，到题库查找相应题目，再把问题交给用户；用户回答后，系统还要把回答和题目对应起来。每一步都要依赖前一步的结果，所以“能调起模型”只是开端。题目有没有查对、问题有没有清楚地提出、回答有没有被正确理解，都会影响下一步。这个项目给我们一个具体入口，来看 Agent 开发里哪些工作仍要靠扎实的软件工程。

这个开发者的项目里，题库提供问题材料，模型参与理解消息和组织交互，程序把相应环节接起来。如果回答匹配得不稳定，系统就难以给出可信的结果；怎样判断匹配，需要结合实际题目要求设计评价方式。[00:05:03]

为什么要逐步检查？模型的输出不能像固定函数那样保证每次完全相同。同一句用户消息可能让模型给出不同表达，也可能在边界情形下理解错误。开发者因此需要在模型外围增加控制和保障代码，这类外围结构常称为 harness。它把输入、提示词、模型输出和后续处理组织起来，并配合检查方法让整个任务能够被调试和验证。

在这个开发者看来，AI 面试项目比他做过的前后端项目都复杂，关键难点就在模型行为带来的不确定性。调试时需要调整提示词，并在流程节点打断点，逐项查看模型产生了什么结果。只看最终页面或一次答对的结果，很难知道问题出在查题、提问还是回答匹配。把各节点输入和输出看清楚，才能定位偏差来自哪一步，再决定要改提示词、程序控制还是测试条件。[00:01:51]

测试也不能只挑模型表现最好的情况。开发者提出，要观察较差和较好的输出，并检查结果能否复现、能否测试、能否逐渐形成标准流程。这些检查回答了不同问题：最差结果揭示系统可能失败到什么程度；重复测试帮助判断一次成功是否只是偶然；流程化检查则让相同类型的任务可以用相近方式评估。只有模型每一步的输出都能被观察，团队才有机会解释失败并确认修复有没有效果。

业务流程越复杂，这种可观察和可评测的要求越重要。一个流程若有多个模型节点，前一步生成的内容会成为后续判断的输入；只看最终答案，就无法区分是检索错了、模型误解了，还是匹配逻辑出了问题。开发者希望让 Agent 在复杂情况下仍能被观察、被评测。逐节点留下检查位置，能帮助团队定位问题并确认修复结果；这也是他认为 Agent 项目比普通框架 Demo 更费工程工作的原因。[00:05:52]

## 从框架 Demo 回到编程基础

他的工程建议是把 Agent 开发看作后端开发的一个分支，因为编程语言、接口、数据库和流程组织仍然是完成项目的基础。只学会某个工作流框架，再把示例程序搭起来，可能还没有经历模型输出检查、流程调试和失败条件测试这些工作。面试时应能解释系统各环节怎样连接、怎样排查问题，以及怎样验证改动；这也是他反对只背项目话术的原因。[00:03:11]

业务能否提供新的价值，也会影响 Agent 是否值得开发。编程工作比较垂直，许多步骤本身就在软件环境里；制造业的利润环节可能还包括售前、售后和供应链，其他行业也有各自的流程。把模型接入这些业务，需要改变已有工作方式，系统和人员之间也会产生协调成本。开发者据此判断，多数行业让代码接管完整流程并不容易，需要逐项解决与原有工作衔接的问题。

关于就业，他个人预测现有 Agent 岗位在未来一到两年内会减少，并认为这类岗位主要出现在有明确垂直业务需求的中大型互联网公司，候选人竞争也很激烈。他用同事、朋友求职经历说明自己的观察；这些经历和预测不构成整体招聘市场的统计。对想进入这个方向的人，复盘强调把编程基础、真实业务分析和模型工程调试连起来，并把框架学习放回这套工程能力之中。

## 总结提炼

AI 面试的流程从用户消息开始，经过题库查询、提问、接收回答和答案匹配。模型输出会变化，因此工程师需要用 harness 串起流程，再通过断点、输入输出检查、边界测试和复现验证找到问题。岗位前景部分是开发者个人判断；项目经验部分则落在可观察、可评测的具体工程工作上。
