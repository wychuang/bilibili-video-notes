团队成员各自用 AI 开发时，同一个坑可能被重复解决：一个人花三小时找到方法，另一个人第二天重新遇到。这个工具介绍提出，把规则、技能和经验放进共享仓库，再经过检索、评审和维护，让后续任务可以找到它们。以下是视频对工具的介绍，功能和兼容范围以实际版本为准。[00:00:23]

## 共享规则，并通过评审修改

第一层把团队的技能、规则、文档、钩子及连接配置放进 Git 仓库。成员通过分支和合并请求提出变更，经过评审后合入；工具在会话开始时同步配置到相应环境。这样团队能看到谁改了什么，并讨论原因。[00:01:25]

Git 保存了变更历史，评审提供检查机会；规则是否准确、同步是否符合每个人的环境，仍需要实际验证。视频提到不同工具和 Git 平台的兼容能力，使用前应核对当前版本及权限。[00:01:56]

## 摩擦信号：何时值得回顾一次会话

会话结束时，工具根据纠正、拒绝调用或反复失败等信号提示可能值得总结的经历。示例中，一次会话出现两次打断和多次工具重试，提示使用者考虑整理并分享问题。[00:02:24]

信号能帮助找到需要回看的地方，却不能自动证明哪一方有错，也不能替代对原始过程和解决办法的核查。分享前还应确认内容是否包含项目机密、个人信息或凭据。

## 检索和维护，让经验能再被找到

视频介绍的第二层提供团队知识检索。搜索“端口冲突”时，结果包含一次代码评审发现的问题和部署配置经验；结果带有来源等信息，便于继续查看。其介绍提到结合关键词检索和代码关系，命中代码时给出文件路径。[00:03:23]

[[FRAME:00:03:28|检索结果把端口冲突相关的两段团队经验放在一起，并保留来源。]]

第三层关注经验的后续使用：有用且经过验证的条目可晋升到正式技能、规则或文档；长时间未使用或过时的条目需要复核与维护。使用次数能提供线索，仍需要人判断适用范围和准确性。[00:04:15]

## 两个需要团队商量的问题

视频提出，若把个人干预次数做成排名，成员可能减少纠正，反而损害依靠摩擦信号发现问题的机制。指标如何使用、谁能看见哪些数据，需要团队明确约定。[00:05:03]

知识库也有长期维护成本：谁负责复核、多久处理过时条目、如何撤回错误规则，都需要分工。工具提供流程后，团队仍要用真实案例检验它是否改善了工作。[00:05:27]

## 总结提炼

共享仓库保存规则变化，摩擦提示帮助发现值得复盘的会话，检索让经验再次出现，评审与维护决定经验能否继续使用。
