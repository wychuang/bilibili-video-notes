多 Agent 的成本，藏在交接处

来源：DeerFlow 2.0 架构解读 · 12 分钟 · 快读。项目功能持续变化，视频中的缺陷清单与基准数字仅作录制时主张。

一句话抓住核心

拆出多个 Agent 前，先证明任务可以独立完成、结果能够可靠合并，而且并行收益值得额外协调成本。

从固定接力到主管分派

视频把早期流程描述为固定接力：协调、规划、研究、成稿依次完成。需求变化后，固定角色和交接顺序可能需要频繁调整。[00:00:50]

随后介绍主管式结构：主 Agent 掌握目标，根据需要派出临时子任务，再收回结果。这使分工可以跟着任务变化，主线状态集中管理。[00:01:40]

术语要注意：主管加子 Agent 也属于层级式多 Agent 设计。没有子 Agent 之间的自由交流，不会让整个系统自动变成只有一个 Agent；讨论时说清控制权、状态和通信方式更有价值。

三类交接损失

第一是上下文丢失。子任务只收到局部提示，可能漏掉最终用户的重要约束。

第二是产物不兼容。一个输出摘要，一个输出代码片段，合并者仍要重做结构与验证。

第三是协调放大。多个任务重复查同一资料、互相等待，或基于不同版本的证据工作，增加成本却没有提升结果。[00:03:25]

因此“开更多 Agent”之前，应该先写清每个子任务的输入、交付格式、依赖和终止条件。

四个可以迁移的工程设计

视频重点介绍中间件、运行核心与应用分离、任务环境路径隔离、渐进加载 Skill。[00:06:15]

它们分别对应四个问题：通用检查放在哪里；换界面时能否复用核心；文件操作能否被限制在任务范围；是否需要把所有技能全文同时放进上下文。

官方项目资料也区分 Harness 与 App，并说明子任务、记忆和沙箱等能力。具体配置和持久化行为应以使用版本为准。DeerFlow 项目说明 · 后端职责说明

虚拟路径只是隔离设计的一部分。仅隐藏真实路径字符串，并不能建立安全边界；实际挂载、权限和网络策略仍须落实。

同样，录制时提到“缺少恢复”“缺少限流”等问题，不宜长期当作项目现状。

迁移练习：让分工证明自己

选同一批研究题，先让单 Agent 完成，再尝试主 Agent 加两个独立子任务。保持资料范围与质量标准一致，记录完成质量、延迟、调用量、重复劳动与合并错误。

只有某类任务稳定受益，再为它保留并行分工。任务高度耦合、共享状态频繁变化时，可以继续采用更简单的组织方式。
