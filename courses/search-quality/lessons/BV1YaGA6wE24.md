# RAG 回答不准，先看资料有没有找到，再看答案有没有照着写

> 来源：[AI大模型-阿水｜面试官问：RAG 准确率怎么从 60% 提升到 85%](https://www.bilibili.com/video/BV1YaGA6wE24/) · 5 分 45 秒 · 深度阅读

一个问答系统答错了，我们第一反应往往是换一个更强的模型。可如果回答所需的那段资料根本没有交给模型，换模型之后，它仍然看不到那段资料。反过来，资料已经找对，模型却在回答时加上没有依据的内容，继续调整检索也未必能解决问题。我们需要先把这两种情况分开，才知道下一步应该检查哪里。[00:00:15]

RAG 的基本过程并不复杂：系统先根据问题查找相关资料，把找到的内容与问题一起交给语言模型，再由模型回答。这让我们至少能检查两个位置：查回的资料是否包含回答所需的信息，最后的答案是否忠于这些资料。标题里的“60% 到 85%”表达了一条优化路线的目标，但这些百分比没有给出完整的测试题、评分定义和各步骤对照结果。因此，下面适合学习的是怎样逐步检查系统，不能把这组数字当作照做必得的收益。

## 找全了没有，与照着写了没有，是两把不同的尺

上下文召回率关注第一件事：回答这道题需要的信息，有多少进入了检索返回的内容。假如正确回答需要三个条件，系统只取回其中一个，后面的模型就缺少两个条件。出现这种情况时，我们要回到资料解析、切分、查询和检索这些步骤，看看信息在哪一步没有进入最终的候选内容。低召回说明存在漏找，但仅凭一个低分，还不能立即断定就是某个 embedding 模型出了问题。[00:00:28]

忠实度关注第二件事：模型写出的内容，是否得到它眼前资料的支持。一个答案可能语句顺畅，却把资料没有说过的细节补了进去；也可能把“在某些条件下成立”写成“一定成立”。这时，即便相关文档已经找到，生成过程仍然需要检查。忠实度评价的是答案与所给资料的关系，资料本身是否正确和最新，还要另外确认。模型忠实复述一份过期说明，也可能给用户带来错误指引。[00:00:44]

| 检查位置 | 我们正在问什么 | 发现问题后先看哪里 |
| --- | --- | --- |
| 检索返回的资料 | 回答所需的信息有没有被找到 | 解析、切分、查询表达和检索结果 |
| 模型生成的答案 | 每项重要说法是否有资料支持 | 提示词、模型对条件的处理和无依据补充 |
| 资料本身 | 这份说明是否正确、适用且没有过期 | 来源、版本及适用范围 |

第三行补充了理解前两项所需的一个区别：找到了资料、照着资料回答，与用户最终得到正确答案之间，还隔着资料是否可靠。这也说明，单独把某个分数做高，无法替代对具体失败案例的查看。

## 文档怎样切，会改变模型能看到什么

为了检索，长文档通常会被分成较小的片段，叫 chunk。最容易实现的做法是按固定长度切开，达到 256 或 512 个 token 就断开；token 是模型处理文字时使用的计数单位，不能直接等同于中文字数。固定长度好管理，但句子的含义不会为了满足长度限制，恰好在边界处结束。一个关键事实的前半句和后半句被切到两边，两份片段都可能单独说不清楚。[00:01:07]

语义感知切分试着利用句子和段落的边界，在相对完整的位置断开。这样，被找回的片段更可能带着完整条件和结论。还可以让相邻片段有一部分重叠：前一片末尾的内容，在后一片开头再保留一次。即使检索只选中了其中一片，边界附近的信息也有机会一起被带回来。重叠越多，重复存储与重复返回的内容也越多，需要根据文档和查询来权衡。[00:01:33]

这里给出的重叠比例是 10% 到 20%，可以把它当作候选设置，而无需理解为固定标准。关键检查仍然很具体：切完后，一个事实的对象、条件和结论是否还在一起？返回某个片段时，读者能否只凭它明白正在说什么？改动前后用同一批问题比较，才能确认这种切分对当前文档有没有帮助。单凭“语义切分”这个名称，还不足以说明每个片段都已经完整。

## 改写问题可以帮助检索，也可能悄悄改变问题

用户很少总是用完整、规范的句子提问。“那个怎么弄”“上次说的那个方案”都很常见。人如果参与了前面的对话，也许知道“那个”指什么；检索程序如果只拿到最后一句话，就没有这样的背景。Query 扩写会尝试利用已有上下文，把口语化提问改写成更完整的查询，让系统更容易找到对应资料。[00:02:08]

危险也正出在“补全”这一步。用户只说“性能优化”，模型却写成“MySQL 数据库的 SQL 查询性能优化”。后面这句话确实更具体，可多出来的 MySQL 和 SQL 未必来自用户。检索按照这个新问题去找，会把其他可能的性能问题排除在外。系统之后即使找到许多高质量的数据库资料，也可能一直在认真回答另一个问题。[00:02:29]

一种检查办法，是分别把原问题和改写结果转成向量，再计算余弦相似度。余弦相似度比较两组向量的方向，通常被用来粗略判断文字含义是否接近；如果相似度过低，就放弃改写，保留原问题。这里提出的 0.8、0.65 到 0.7 等阈值，都需要用实际数据校准。不同 embedding 模型和不同类型的问题，分数分布可能不同。[00:02:49]

还要理解这个检查的边界：“性能优化”和“MySQL 性能优化”在主题上依然很接近，相似度较高，也无法证明新加的限定有根据。向量分数可以帮助发现明显偏离，却无法自动确认每个补充条件都来自用户。回到原问题和已有对话，检查改写究竟增加了什么，仍然很重要。这个例子最值得记住的地方，就是检索词越具体，并不总代表它越准确。

## 两种检索找到不同的东西，分数也不能直接当成一把尺

向量检索擅长发现含义接近的表达。问题和文档用词不同，仍然可能被联系起来。但专有名词、代码片段、版本号往往要求精确匹配，关键词检索在这些地方很有价值。混合检索会分别运行这两条路径，把两边找到的候选内容放到一起，再决定哪些优先交给回答模型。[00:03:17]

现在又遇到一个实际问题：两边分数的含义不同。向量检索可能给出余弦相似度，关键词检索可能给出 BM25 分数。BM25 根据查询词在文档中的出现情况等因素计算相关程度，它的数值范围与向量相似度不同。因此，我们不能看到一条结果是 8 分、另一条是 0.8 分，就直接认为前者好十倍。这两个数字来自不同的计算办法。[00:03:41]

这里提出的方案是 LambdaMART，一种学习排序的方法。我们把 BM25 分数、向量相似度、实体是否匹配等作为特征，让模型根据已有的相关性样例学习怎样排列候选。实体匹配可以理解为问题中明确提到的对象，在候选资料中是否对应得上。学习排序需要可用的训练样例和评价方式；它提供了一种综合多路信号的办法，并不意味着每个混合检索系统都必须使用这一种排序模型。[00:03:50]

## 把时间花在确实需要细查的问题上

如果每个问题都跑多路检索，再逐条重排序，回答时间可能变长。于是可以增加一个路由步骤：先用较轻量的方法判断当前问题适合走哪条处理路径。这里的方案给简单问题使用较快的检索流程，复杂问题再使用混合检索和重排序。路由就是把不同查询分配给不同处理方法，不需要把这个词想得很神秘。[00:04:08]

这种分配能否有效，还要看分类是否准确。一个看起来很短的问题也可能包含关键版本号，需要精确匹配；一个很长的问题也可能只是在重复同一项需求。把复杂问题错送到简化流程，可能会损失回答质量。因此，我们需要同时观察回答效果和耗时，检查哪些问题走错了路。快速路径与深度路径的具体安排，要服从实际题目的表现。

到这里，几项改动就接起来了。切分决定检索能拿到怎样的信息单元；查询改写决定我们拿什么问题去找；混合检索与排序决定哪些候选被留下；路由决定每个问题要经过哪些处理步骤。任何一步改变之后，都应回到同一批测试题，再看该找的信息有没有找全，答案有没有无依据的补充，耗时是否在可接受范围内。[00:04:41]

## 总结提炼

### 一句话抓住核心

先区分漏找资料和无依据生成，再沿切分、问题改写、检索排序与路由逐步检查，每项改动都用实际问题验证。

### 推理主干

资料没找全，模型就缺少作答条件。资料找全以后，模型仍可能添加资料没有支持的内容。优化要沿着这两个失败位置展开，同时留意改写问题造成的偏移，以及更复杂处理带来的等待时间。

补充练习：找一个确实回答错误的问题，把原问题、返回片段和最终回答放在一起。先指出哪项必要信息缺失，或哪句话没有资料支持，再提出一项与这个错误位置有关的改动。面试时也可以沿这个顺序解释；没有亲自做过的优化和测量结果，不要写成自己的项目经历。
