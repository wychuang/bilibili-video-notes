接入知识之前，先选一条最短的路

来源：blackstone_99 · RAG 五条路线对比 · 11 分钟 · 自动转写。录制中的价格、产品能力与行业判断具有时效性。

一句话抓住核心

先弄清数据长什么样、问题需要怎样查、用户能等多久，再选择检索架构。

同样是“给 AI 一点资料”，其实有五种任务

假设我要让 AI 回答公司制度问题。只有十页稳定的制度，和每天变化的百万条业务记录，需要的系统会完全不同。视频先用两个问题划分场景：资料是否能放进上下文？查询需要精确匹配，还是模糊的语义理解？[00:00:55]

路线 适合尝试的情况 最先检查的代价
长上下文与缓存 资料量可控，经常重复使用 实际 token 数、缓存命中、长文本遗漏
检索增强生成 大量文档中寻找相关段落 解析、切块、召回、排序、引用是否可靠
Agent 自主检索 要反复查找并追踪线索 调用次数、延迟、停止条件
SQL 或业务 API 数据已经是结构化表格或业务记录 字段含义、查询正确性、权限
深度研究流程 一个问题需要多来源、多步骤调查 预算、等待时间、来源质量

“几百份文档”只是视频中的粗略说法。十页文档和千页文档不能按同一个份数计算；能放下也不代表能稳定读对。[00:02:18]

精确的东西，先尝试精确地找

函数名、错误码、配置键通常有确定写法。关键词搜索找到定义，继续读调用方，可能比把每个文件向量化更直接。反过来，用户说“我总觉得这里不安全”，没有准确术语，语义检索就更有价值。[00:01:42]

代码检索还常常需要多跳：找到函数，看它调用谁，再检查配置。Agent 可以根据前一次结果决定下一步。这个循环也会积累调用成本，需要步数上限和可解释的终止条件。[00:04:43]

对于数据库中的订单总额，优先考虑查询数据库。把数值表格切成文本，再靠语义相似度凑出统计结果，会多出不少出错机会。查询仍需校验，尤其要限制修改、删除及敏感字段访问。[00:06:13]

用上 RAG 后，别只盯着向量模型

视频把混合检索、重排序、给片段补足上下文列为可尝试的升级：关键词召回保住专有名词，语义召回覆盖不同说法；重排序进一步比较问题与候选内容；片段上下文帮助识别“这个数值究竟属于哪一年、哪家公司”。[00:03:24]

这些方法都要通过同一套测试来判断。视频中的“提升十倍”“降低到三分之一”等概括缺少本地任务的完整实验条件，不能直接作为自己的预期收益。

评测和整理数据，要先于架构竞赛

一张表被切碎、过期制度排在最新制度前面、某个字段单位丢失，都可能让复杂系统给出错误回答。换更强模型未必能补回丢失的信息。[00:07:48]

先收集一批实际问题，记下应该找到哪份资料、哪些条件必须保留、什么时候应该说明证据不足。每次改动后重跑。模型说得流畅，只说明它能组织语言，资料是否找全仍要另外检查。

迁移练习：给三个问题分路由

分别考虑“这份合同的违约条款是什么”“上月各地区订单总额是多少”“两个竞争产品未来半年可能怎么发展”。为每题写出最轻的可行路线、需要的证据和停止条件。

最后加一个约束：如果只能等五秒，方案怎样变化？如果允许等五分钟，又多了哪些值得做的检查？这些约束比跟随架构热词更接近产品决策。
