# Agent 面试为什么会一路问到数据库、消息队列和效果验证？

> 来源：[我的 AI Agent 面试复盘](https://www.bilibili.com/video/BV1hubZ6WEfU/) · 假如今天可以躺平 · 约 36 分钟 · 深度阅读

简历里有一个车辆故障诊断项目：用户输入故障码，系统查技术手册，再由模型分析可能的故障原因。为了介绍实现，我们很容易列出几个名字：用了 LangGraph，接了 RAG，还安排了多个 Agent。可面试官接下来只要问一句“为什么需要多个 Agent”，介绍就可能停住。项目做过，代码也能运行，却还没有把某个设计和它解决的具体问题联系起来。

这份面试复盘围绕的，正是这些联系。不同面试从车辆诊断、客户端性能、数据库查询和订单状态机进入，最后都追问系统在真实条件下怎样运转。下面保留几场面试的主要问题，以及求职者事后形成的理解。这些是个人经历和回顾，不能当作相关公司的统一题库，也不能用来保证其他岗位会采用相同考核方式。[00:00:19] [00:02:22]

## 先让一项任务完整地走完：客户端为什么变慢了？

在小红书的一场面试中，问题先从前端性能工作问起，随后进入一个具体场景：应用启动到用户看见首屏，中间分成多个阶段，每个阶段都有记录耗时的数据。工程师平时通过 SQL 查询这些数据，比较不同日期或版本。如果网络阶段变慢，就继续查网络相关指标；如果图片加载变慢，就继续检查图片这一部分。题目希望把这种分析工作交给 Agent。[00:03:36]

理解这个题目，可以跟着工程师原来的工作走一遍。首先需要取得正确的数据，知道比较的是哪两个版本、什么时间范围。接着找出变化比较明显的阶段，再根据阶段选择更细的查询。得到细分结果以后，还需要结合业务背景解释哪些原因值得检查，最后形成一份让人能够继续处理的报告。每一步都依赖前一步提供的内容，不能只把所有数字交给模型，让它自由写一篇分析。

求职者最初提出了取数、异常检测、选择问题阶段和生成归因报告的安排。面试官随后加上一个限制：报表数字必须精确，而且现有查询接口相对固定。这个条件会直接改变设计。既然 SQL 和计算逻辑已经可以确定，就可以把它们写成可测试的查询或脚本；模型需要不同维度时，调用对应接口并填写参数。模型再根据返回结果选择后续分析方向、组织解释。[00:04:44] [00:06:46]

这样分工，才能分别检查两类问题。报告说耗时增加了多少，可以沿着查询和计算追溯；报告说某种变化可能由网络因素引起，则需要检查这个判断使用了哪些信息。固定程序也会写错，查询口径也可能不合适，所以程序输出仍需测试。模型生成的原因解释则应该保留为有待证实的分析，不能因为语言完整就当成已查明的原因。

[[FRAME:00:07:38|查询与聚合计算单独处理，模型负责理解上下文和选择分析路径；数字与原因解释因而能够分别检查。]]

这个系统甚至可以没有聊天框。它可以按计划读取昨天的数据，发现某一阶段退化，继续检查并给工程师发送报告。聊天只是一种交互入口，任务如何被触发、需要哪些信息、何时完成，同样值得设计。对面试题来说，说明这条完整工作过程，比单独解释“Agent 是什么”更接近业务问题。[00:06:02]

## 路径要写死到什么程度，模型又能自行决定什么？

第二轮继续问：多个 Agent 串起来，是否只是提前编排好的逻辑链？如果所有任务都按 A、B、C 的顺序运行，每一步做什么也已经确定，那我们首先拥有的是一条工作流程。把步骤改名，并不会自动增加自主能力。此时需要解释，模型在哪一步需要根据新信息做出不同选择。[00:08:10]

完全固定的流程容易检查，因为可能的路径比较清楚；它遇到未预料的情况时，也可能不够灵活。完全交给模型规划，则会增加另一组风险：它可能反复查询同一件事，绕开必要检查，或者消耗过多调用次数。两端之间有许多可选安排。求职者倾向保留业务上的关键限制，让模型在局部选择工具、检索方向和分析路径，再把选择结果交回流程处理。

仍以性能分析为例，查询哪些时间范围、哪些数据可以访问，可以由程序限制；在发现图片加载耗时上升后，先查看哪个相关指标，可以留给模型判断。这样描述，读者才能看清“动态”具体发生在哪里。我们也有了可以继续追问的对象：如果模型一直找不到原因，何时停止？如果下一次查询越过权限范围，谁来拒绝？灵活性越大，需要说明的边界通常也越多。[00:08:36]

“为什么要多 Agent”是同一个问题的延伸。不同阶段如果确实需要不同工具、不同上下文，或者承担可以独立检查的职责，拆分角色可能有帮助。但这些理由仍然需要和更简单的实现比较。几个普通函数或一条固定流程已经足够时，多加角色会增加交接、调试和调用成本。面试里值得说明的是，某次拆分究竟减少了什么困难，又引入了什么代价。[00:16:05]

## 技术手册怎样切开，才不会把问题和答案分开？

在阿里的面试中，追问从 RAG 开始。RAG 可以先理解为：回答问题前，先从资料里找到相关内容，再让模型结合资料作答。车辆故障诊断的资料来自技术手册，所以检索质量首先受手册怎样整理影响。面试官问的“文档怎么切片”，实际是在问，系统拿给模型阅读的每一小块资料，是否保留了足够的意思。[00:09:54]

技术手册往往有车型、故障码、故障现象和处理办法等结构。如果每隔固定长度切一刀，故障现象可能在上一块，处理步骤却在下一块。检索恰好找到现象那一块，模型仍然拿不到处理方法。即便每一块都转换成向量——一组用于比较语义相近程度的数字——这种转换也不会自动把已经丢失的上下文补回来。

求职者因此讨论先按标题和章节划分，再处理过长章节的办法。对于太长的内容，可以继续切成有一定重叠的小段，让相邻段落保留一点共同内容；同时保存车型、故障码和所属章节等元信息。元信息就是附在正文旁边、说明这段内容属于哪里的资料。这样，检索和回答时更容易知道一段处理步骤适用于什么车辆和问题。[00:10:20]

这个回答没有提供一个对所有文档都合适的长度。它给出的理由来自手册本身：结构清楚，就尽量利用结构；章节太长，再补充长度控制。换成聊天记录、表格或代码，原来的划分方式可能需要改变。面试官继续问“为什么”，就是希望看到这种从材料条件走到设计选择的关系。

## 为什么这个阶段只需要一个轻量的向量库？

切好资料以后，要把资料向量存起来并完成相似检索，于是自然会问数据库选型。复盘里的原型只处理几十份技术手册、成千上万段切片，供内部低频使用，需要快速修改。这样的条件下，先采用轻量方案，有机会减少部署和维护工作。这里的“轻量”说明的是当前负担较小，并不代表永远不需要扩展。[00:11:15]

如果之后要让多个客户独立使用，持续更新大量文档，处理更高并发，还要保证服务在部分机器出故障时继续运行，选择依据就会改变。多租户、更新方式、并发和可用性，分别对应不同需求。一个完整回答需要说清眼下有哪些需求，哪些尚未出现，以及观察到什么变化时会重新评估。背出数据库优缺点，可以帮助比较；把比较放回自己的数据量和使用方式，才能解释这次选择。

随后还有状态与存储的问题。LangGraph 中的 state，可以理解为任务执行到当前时刻需要保留的信息。在车辆诊断里，它可能包括用户输入、车辆信息、故障码和已有检索结果。某个节点读取这些信息完成分析，再把新的结果写回，后续节点才知道接下来基于什么继续工作。说清这些具体内容，比只说“使用状态机”更能让人理解系统。[00:13:35]

任务执行中断后，内存里的信息可能丢失，因此还要讨论保存位置和恢复方式。LangGraph 使用 checkpointer 保存一次执行线程的状态快照；需要跨重启恢复时，也要选择能够持久保存的实现，内存实现本身不满足这一条件。有关这些概念可参见 [LangGraph 的持久化说明](https://docs.langchain.com/oss/python/langgraph/persistence)。不过，状态存下来只解决了部分问题，已经执行过的外部操作是否会重复，仍然需要另外处理。[00:15:08]

## Agent 接入业务以后，消息为什么也成了面试题？

追问随后转向 Kafka：高峰期消息为什么堆积，消费速度为什么跟不上，CPU、网络和其他依赖有没有成为限制。Kafka 可以把持续到来的事件保存起来，让负责处理事件的程序逐步读取；读取并处理消息的程序通常称为消费者。Agent 如果由这些事件触发，就同样会遇到处理速度落后于到达速度的问题。模型调用变慢、工具接口拥堵、消费者本身计算繁忙，都可能使后续事件等待更久。[00:17:19]

因此，看到队列变长，不能直接断定多加几个消费者就能解决。我们还需要看看任务分布在哪里、消费者花时间等待什么、真正耗时的是哪一个环节。Kafka 把一个主题的消息分到多条有序记录里，每条称为一个分区。在传统消费者组的分配方式下，同一分区在同一组内交给一个消费者处理，消费者数量增加也受到分区安排影响。关于这一关系以及消息处理语义，可参见 [Kafka 的设计说明](https://kafka.apache.org/40/design/design/)。面试里的追问，希望候选人能沿着实际处理过程缩小问题范围。

消息重复也是同样具体的困难。程序已经完成一个外部操作，但还没记录自己处理到了哪里就退出了；重新启动后，可能再次收到那条消息。如果这条消息会改变订单或资金状态，重复处理就可能产生重复副作用。因此需要考虑幂等性：同一请求即使再次到来，也不能把本该发生一次的业务动作又做一遍。消息系统的保证有适用范围，不能直接推导出所有外部调用都只会发生一次。[00:18:00] [00:24:43]

求职者在字节相关面试中，又遇到了消费者组、分区、重平衡、offset 提交、缓存和并发等问题。它们和 Agent 的联系由此很清楚：模型只是整个软件的一部分，事件怎样进入、任务怎样保存、失败怎样重试，都决定了最后的业务结果。学习模型和框架以后，原有的软件工程基础仍然有实际用处。

## “卖得最好”到底在查什么？

Text-to-SQL 的任务，是让用户用自然语言提出问题，再由系统生成 SQL 查询数据库。一个看起来很简单的请求是：“帮我查一下卖得最好的几个商品。”但“最好”可以指卖出的数量，也可以指销售金额。两种查询都可能返回格式正确的数字，排名却不同。系统在没有确认含义时直接选择一个口径，就可能非常精确地回答了另一个问题。[00:18:37]

这时，澄清本身就是任务的一部分。系统可以先问用户关心销量还是销售额，再继续查询。让模型自报一个很高的信心分数，并不能替代对业务含义的确认。特别是会改变结果的重要歧义，应该有明确的处理方式。相同道理也适用于何时拒绝请求：用户要求访问没有权限的数据时，系统应当在执行层限制访问，不能仅靠模型愿意遵守一句提示词。[00:19:14]

含义确定以后，模型还需要知道数据库有哪些表、字段表示什么、表之间怎样关联。schema 是数据库结构的说明，metadata 则可以包含字段解释等辅助信息。把相关结构和业务口径提供给模型，才能减少它凭名称猜测的空间；对重要指标，还需要检查查询结果和预期口径是否一致。多表查询写得出来，与这次查询确实回答了用户问题，是两个需要分别确认的结果。[00:19:46]

## 四十多分钟的 AI 编程考核，人在负责什么？

复盘里还有一次允许使用 AI 的现场编程，题目是设计一个可扩展、线程安全、逻辑清楚的订单状态机。状态机规定订单有哪些状态，以及收到某种事件后，可以从哪个状态转到哪个状态。线程安全则要求多个执行过程同时操作时，也不能把这些规则破坏。题目给出背景、功能和限制，候选人需要在有限时间里把它们变成实际设计。[00:21:12]

求职者后来向面试官了解，对方在意如何使用 AI。他将自己的角色理解为负责设计与检查的人，将 AI 当成帮助实现局部内容的开发者。按照这个理解，第一步是先读懂条件，形成初步结构；接着拆出能够分别讨论和验证的部分，再请 AI 帮助编写。每完成一部分，都要读代码、运行测试，检查边界情况。这样，候选人才能解释某个结果为什么符合题目要求。

这也解释了为什么只把整道题交给 AI，会使后续追问变得困难。模型选了一种状态表示方式，面试官问它与另一种表示方式各有什么代价；如果候选人从未考虑这一选择，就难以说明改变需求以后会怎样。使用 AI 并不自动消除设计工作，它让我们能够更快得到一个实现，但还需要判断这个实现是否合适。[00:22:44]

这场考核的重点，不能推广为所有编程面试已经改变的统一趋势。它至少提供了一个明确的准备方向：对于自己实际使用 AI 完成的代码，能够说明输入条件、主要决策、测试结果和未解决的问题。模型提供的解释可以帮助思考，代码运行和可复现的测试则提供更直接的检查依据。

## 一句“调用工具”，省略了多少需要负责的事情？

另一次追问认为，项目听起来很简单：输入进来，Agent 判断，调用工具，输出结果。这个概括并没有错，但省略了调用之前和之后的条件。谁能使用这个工具？读取资料和修改资料是否拥有相同权限？参数格式正确以后，参数内容是否仍然可能越权？高风险动作是否需要确认？这些问题会决定一条看起来很短的调用能否安全进入真实业务。[00:25:12]

如果工具允许执行模型生成的 Python，问题还会继续。代码在哪里运行，能访问哪些文件和网络，最多使用多少时间与资源，超时以后怎样停止？沙箱的作用，是把执行放到受限制的环境里，减少对其他系统的影响。限制需要由程序和运行环境实际执行，不能把“请勿访问未授权文件”写在提示词里就视为已经隔离。[00:26:01]

一张流程图可以只画输入、模型、工具和输出，但介绍真实项目时，我们需要把最重要的限制补回来。模型如何决定下一步，和系统如何控制这一步的后果，都属于设计。求职者由这些追问意识到，服务化、存储、网络、监控和故障恢复并没有从 AI 工程里消失。

## 错误案例消失了，怎样知道哪项改动有效？

最后一组面试问题涉及 Skill。这里可以把 Skill 理解为供 Agent 使用的一组任务知识和操作指导，工具则负责实际执行某项能力。复盘谈到 Skill 怎样选择、更新和管理版本，随后追问效果：上线一版新方案，看到结果变好，能否说明其中某个 Skill 确实起了作用？[00:28:01]

这个问题难在，整体结果可以受很多变化影响。新 Skill 上线以后，原先的错误案例不再出现，可能是规则发挥了作用，也可能是来了不同类型的请求，或者上游系统同时修复了问题。只看错误数量下降，还无法知道哪种解释成立。甚至连“消失”也要具体看：是同类请求继续到来并被正确处理，还是这类请求暂时没有出现？[00:29:08]

[[FRAME:00:29:57|追问从方案整体有效，进一步问到 Skill 的贡献，以及错误案例消失以后怎样继续验证。]]

求职者在事后提出几种思路。保留一部分不使用新 Skill 的对照流量，可以比较相近条件下两种处理的差异；维护历史错误的回归测试集，可以让旧问题再次进入系统，看看新旧版本分别怎样回答；记录 Skill 是否被调用、相关指导是否在执行中起作用，则有助于检查变化发生在哪里。这些办法各自提供一部分信息，需要根据任务条件组合使用。[00:29:45]

其中，回归测试比较容易理解：过去有一道题经常答错，我们把这道题留下来，修改后再跑一次。它能说明系统对这道保留的问题是否改善，但不能独自保证未来所有问题都改善。对照流量更接近日常使用，仍需考虑分组方式、样本量和观察时间。日志可以告诉我们新 Skill 是否参与了某次处理，但“调用以后恰好答对”也不能单独证明因果。把每种观察能说明什么讲清楚，评价才不会超出材料本身。

面试官还问，五段调用了不同 Skill 和工具的成功会话，怎样合成一个 Skill 的优化方向。这里首先要分清成功发生在什么条件下：是哪条指导有帮助，工具结果是否相同，几段会话是否解决同一类困难。五次成功经过可以提供线索，但不能仅凭它们都成功，就把所有操作合并成一条普遍规则。优化对象越明确，后续越容易设计比较和回归检查。[00:30:04]

## 总结提炼：顺着项目，准备能够继续解释的内容

这些经历共同指向一种准备方式：把自己做过的任务，从输入一直讲到结果，再检查中间每一个重要选择是否有理由。实际做过的内容和设计设想也要分开。没有在生产环境实践过，可以说明目前的理解、需要确认的条件和计划怎样验证；把尚未做过的事情写成已有经验，会让后续追问越来越难回答。[00:33:51]

| 面试追问 | 需要展开的具体关系 |
| --- | --- |
| 为什么这样切文档？ | 手册结构怎样影响资料是否完整，切分怎样保留适用条件 |
| 为什么选这个数据库？ | 当前规模和使用方式需要什么，什么变化会触发重新选择 |
| 为什么要多个 Agent？ | 不同职责、上下文和工具怎样拆分，增加的协调成本是否值得 |
| 任务失败后怎么办？ | 状态保存到哪里，哪些操作可能重试，怎样避免重复副作用 |
| 允许 AI 写代码时，你做了什么？ | 怎样理解限制、作出选择、拆分任务和检查结果 |
| 错误减少，能证明更新有效吗？ | 是否处理同类请求，有何对照，回归与日志各自支持什么判断 |
